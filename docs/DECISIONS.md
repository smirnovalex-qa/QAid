# Журнал архитектурных решений (ADR)

Формат: каждая запись — краткий ADR (контекст → решение → следствия). Новые решения добавляются в конец с инкрементом номера и не переписывают старые: устаревшее помечается статусом `Superseded by ADR-XXXX`.

Статусы: `Accepted` · `Proposed` · `Deprecated` · `Superseded`.

---

## ADR-0001: TypeScript strict как основной язык
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Расширение работает с чувствительным контекстом (storage, будущий доступ к сети/DOM). Нужна максимальная защита от ошибок на этапе компиляции.

**Решение.** TypeScript 5.x в strict-режиме со всеми строгими флагами, включая `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`.

**Следствия.** Выше порог входа, но меньше рантайм-багов. Все публичные API — типизированы; `any` запрещён линтом (`no-explicit-any`).

## ADR-0002: Preact вместо React
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Для расширения критичен размер бандла (popup должен открываться < 150 мс). React тянет заметный вес.

**Решение.** Preact + `@preact/signals`. При необходимости совместимости с экосистемой React — через `preact/compat` точечно.

**Следствия.** Малый бандл, простая реактивность через сигналы. Риск: часть React-библиотек несовместима — оцениваем перед добавлением зависимости.

**Альтернативы:** React (тяжелее), Svelte (иной билд-пайплайн, меньше знакомость), vanilla (дороже поддержка UI).

## ADR-0003: Vite + @crxjs/vite-plugin как сборка
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Нужна быстрая сборка MV3 с HMR и корректной обработкой манифеста, service worker и нескольких точек входа.

**Решение.** Vite + `@crxjs/vite-plugin`; манифест описывается типизированно через `defineManifest`.

**Следствия.** HMR для popup/side panel, автоматическая обработка ассетов. Зависимость от актуальности плагина под свежие требования MV3 — держим версию под контролем.

## ADR-0004: Чистая логика отдельно от UI
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Инструменты (генераторы, декодеры) — по сути чистые функции. Их легко тестировать в изоляции.

**Решение.** Каждая фича делится на `logic.ts` (чистая, без Preact/Chrome) и `ui.tsx` (представление). Логика покрывается юнит-тестами близко к 100%.

**Следствия.** Высокая тестируемость и переиспользуемость; небольшой оверхед на структуру каждой фичи.

## ADR-0005: chrome.storage.local через типизированную обёртку
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Прямое использование `chrome.storage` рассыпает нетипизированные ключи по коду и не защищает от повреждённых данных.

**Решение.** Единая обёртка `shared/storage.ts`: типобезопасные get/set/watch, версионируемая схема настроек с миграциями, валидация zod, фолбэк на дефолты при повреждении. Неймспейс ключей `qatoolbox:<feature>:<key>`.

**Следствия.** Централизованный контроль над персистом; миграции обязательны при изменении схемы (см. TASK-005).

## ADR-0006: Криптостойкая случайность для тест-данных
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** `Math.random` смещён и непредсказуемо распределён; для генераторов важна равномерность и отсутствие modulo-bias.

**Решение.** Общий util `shared/random.ts` поверх `crypto.getRandomValues` с rejection sampling для несмещённого выбора из алфавита. Хэши — через `crypto.subtle`.

**Следствия.** Корректное распределение (проверяется статистическими юнит-тестами). Небольшая доп. сложность в выборке без смещения.

## ADR-0007: Local-first, никаких сетевых вызовов в ядре
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Главный дифференциатор и аргумент для enterprise — приватность. Инструмент имеет широкие права, поэтому доверие критично.

**Решение.** Ядро не выполняет сетевых запросов. Запрет `fetch`/`XMLHttpRequest` в коде ядра проверяется линт-правилом и/или тестом. Телеметрии по умолчанию нет.

**Следствия.** Будущий мокинг сети (перехват) — отдельный, явно изолированный модуль с явными правами, не нарушающий этот инвариант для остального ядра.

## ADR-0008: zod для рантайм-валидации границ
**Статус:** Accepted · **Дата:** 2026-08-31

**Контекст.** Данные из storage и межпроцессные сообщения приходят как `unknown` и могут быть повреждены/подделаны.

**Решение.** zod-схемы валидируют все внешние границы: сообщения (`shared/messaging.ts`), настройки (`shared/storage.ts`). Типы выводятся из схем (`z.infer`).

**Следствия.** Единый источник правды «схема = тип»; небольшой вес zod оправдан для границ (в чистую логику не тянем без нужды).

## ADR-0009: Open-core лицензирование
**Статус:** Accepted · **Дата:** 2026-08-31 · **Финализировано:** 2026-09-01 (TASK-001)

**Контекст.** PRD закладывает open-core: бесплатное ядро + платные командные фичи. Нужен выбор лицензии ядра.

**Решение.** Ядро — под **Apache-2.0**. Выбор из двух пермиссивных вариантов (MIT / Apache-2.0) сделан в пользу Apache-2.0 из-за явного патентного гранта (§3) и termination-оговорки — существенно для инструмента с широкими правами и enterprise-аудиторией. Файл `LICENSE` добавлен в TASK-001; `license: "Apache-2.0"` в `package.json`.

**Следствия.** Влияет на приём внешних контрибуций (при необходимости — CLA/DCO) и на упаковку платных модулей отдельно. Платные командные фичи (R3) поставляются как отдельные модули под коммерческой лицензией, ядро остаётся Apache-2.0.

**Альтернативы.** MIT (отвергнут: нет явного патентного гранта).

## ADR-0010: Федеративный протокол сообщений (без центрального union)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Черновой протокол (TASK-003) предполагал центральный `z.discriminatedUnion` и карту `ResponseSchemaByType`, которые обязана править **каждая** сетевая фича (инспектор, storage, мок). Это прямой чокпоинт: merge-конфликты, связность и нарушение принципа «фича = один каталог + одна регистрация». Риск переписываний растёт с числом фич.

**Решение.** Протокол открыт для расширения без правки центрального файла:
- **Типы** — declaration merging открытого `interface MessageContracts` (`shared/messaging/contract.ts`); фича добавляет свои `type → {request, response}` в собственном `messages.ts`.
- **Рантайм** — реестр схем (`shared/messaging/registry.ts`): `defineMessage(type, reqSchema, resSchema)` кладёт zod-схемы в map; валидация на границе идёт по схеме, найденной по `type`. Статический `discriminatedUnion` не нужен.

Центральный `contract.ts` содержит только пустой интерфейс и производные хелперы (`AnyMessageType`, `RequestOf`, `ResponseOf`).

**Следствия.** Добавление сообщения не трогает ядро; типобезопасность и runtime-валидация сохраняются. Architecture-fitness тест проверяет, что у каждого зарегистрированного `type` есть парная response-схема. Минус: declaration merging менее очевиден для новичков — задокументировано в ARCHITECTURE §5 с примером.

**Альтернативы.** Центральный union (отвергнут: чокпоинт); барель, собирающий union из экспортов фич (требует централизованного перечисления типов — тот же чокпоинт мягче).

## ADR-0011: Дескриптор возможностей фичи (capability descriptor)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Черновой `FeatureModule` описывал только UI-панель (`id/title/icon/Component/surface`). Реальным фичам (инспектор, storage, мок) нужны также background-хендлеры, content/page-скрипты, optional-права, схема настроек, i18n, события. При «тонком» дескрипторе всё это протекало бы напрямую в `background`, `manifest`, i18n-каталоги — то есть в код, который мы обещаем не трогать при добавлении фичи.

**Решение.** `FeatureModule` расширен до полного дескриптора возможностей (см. ARCHITECTURE §7): опциональные поля `permissions`, `messages`, `backgroundHandlers`, `content`, `settings`, `i18n`, `events`, `teardown`. Ядро подключает каждый аспект генерически (background итерирует реестр, брокер запрашивает права, загрузчик i18n мёржит фрагменты, storage инициализирует namespace).

**Следствия.** Фича становится действительно самодостаточной; инвариант расширяемости (ARCHITECTURE §1, §13) выполним. Оверхед: дескриптор объёмнее, но все поля кроме базовых — опциональны (простые popup-фичи заполняют минимум).

## ADR-0012: Мост сообщений между средами (UI/background/content/MAIN-world)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Модель сообщений покрывала только UI↔background. Но инспектор (P0, R1.1) требует content-скрипта, а мок (R2) — перехвата `fetch`/`XHR` в MAIN world, у которого нет доступа к `chrome.*` и который общается с расширением только через `window.postMessage`. Это самая сложная часть расширения; если её не заложить в модель заранее, первая же content-фича заставит переписать шину.

**Решение.** Единый API `sendMessage`/`registerHandler` поверх сменных транспортов (`shared/messaging/transports.ts`): `runtime` (UI/content→background), `tabs` (background→content), `window` (content↔page). `content/relay.ts` мостит MAIN↔background с валидацией zod, корреляцией по `correlationId` и фильтрацией по `event.source`/сигнатуре-маркеру. Контракт и релей заложены сразу, реализация конкретных инспекторов — в их волнах.

**Следствия.** Инспектор/мок подключаются без переписывания шины. Безопасность: страница не может подделать команды расширению (фильтрация в релее). Минус: небольшой каркас, не используемый фичами первой волны.

## ADR-0013: Брокер optional-permissions (least-privilege в рантайме)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** PRD требует минимальных прав по требованию (`activeTab`, `scripting`, `declarativeNetRequest`, `debugger`). Без единого механизма это прикручивалось бы ad-hoc в каждой фиче, а страх широких прав — ключевой риск PRD.

**Решение.** Манифест держит только всегда-нужные права (`storage`, `sidePanel`); остальное — в `optional_permissions`/`optional_host_permissions`. Фича декларирует нужные права в дескрипторе; брокер `shared/permissions.ts` (`ensure`/`has`) запрашивает их через `chrome.permissions.request` при первом использовании (пользовательский жест). Отказ не роняет расширение.

**Следствия.** Добавление «тяжёлой» фичи — вопрос декларации, а не правки центральной логики. Каждое право документируется в `docs/PERMISSIONS.md`.

**Правка (2026-09-19).** `ensure` больше **не вызывает `chrome.permissions.request` безусловно**. `chrome.permissions.request` требует активного пользовательского жеста и в ряде контекстов (side panel) отклоняется «must be called during a user gesture» даже для УЖЕ выданных прав — из-за чего повторные действия фичи после первого гранта могли молча падать (напр. запись сети/таймлайна в bug-report). Теперь: (1) **быстрый путь по кэшу** — если право уже подтверждено (кэш `has`/предыдущий `ensure`), возвращаем `true` синхронно, без `request()` (жест для настоящего первого запроса не теряется — никаких `await` перед `request()`); (2) **деградация к `contains()`** — если `request()` всё же кинул, проверяем без жеста: право могло быть выдано как часть более широкого набора или в прошлой сессии (холодный кэш). Отказ пользователя (`request()`→`false`, не throw) по-прежнему честно даёт `false`. Инвариант «`ensure` — только под жестом» сохраняется для реального первого гранта.

## ADR-0014: Кросс-браузерный адаптер платформы (webextension-polyfill)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** PRD закладывает Firefox/WebExtensions во вторую очередь. Прямой хардкод `chrome.*` по всему коду означает проход по всем файлам при порте (callback-vs-promise различия, неймспейс `browser` vs `chrome`).

**Решение.** Весь доступ к WebExtensions API — через `src/platform/index.ts`, ре-экспортирующий `browser` из `webextension-polyfill` (promise-based, работает в Chrome и Firefox). Прямое обращение к `chrome.*` вне `src/platform` и тонких транспортов `shared/messaging` запрещено ESLint-правилом.

**Следствия.** Порт на Firefox — преимущественно вопрос манифеста и точечных API-различий, а не массового рефакторинга. Минус: тонкий слой косвенности и ~кб зависимости.

**Альтернативы.** Хардкод `chrome.*` (отвергнут: дорогой порт); собственная тонкая обёртка (дублирование зрелого polyfill).

## ADR-0015: Cross-feature шина событий (обмен данными без связывания)
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Дифференциатор PRD — «общие пресеты между инструментами» (генератор питает автозаполнение форм). Прямые импорты одной фичи из другой нарушили бы feature-isolation и создали бы графы зависимостей, ломающиеся при удалении фичи.

**Решение.** Типизированный pub/sub `shared/events.ts` с открытым интерфейсом `AppEvents` (declaration merging, как у сообщений). Фичи публикуют/потребляют события по контракту, не импортируя друг друга. Пример: `presets:dataset:changed`.

**Следствия.** Фичи связаны только контрактами событий; удаление издателя не ломает подписчика по компиляции (подписка просто не срабатывает). Минус: косвенность потока данных — компенсируется типизацией событий и тестами.

## ADR-0016: Версионируемый конверт сериализации
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Помимо настроек (у них уже есть миграции, ADR-0005), появятся экспортируемые/шарящиеся артефакты: сценарии моков (R2), «экспорт состояния бага» (R3), синк настроек (P2). Без единого версионирования старые файлы/шаринги ломали бы импорт после эволюции схемы.

**Решение.** Единый конверт `Envelope<K, T> = { kind, schemaVersion, data }` и `shared/serialization.ts` с `pack`/`unpack` и реестром миграций по `kind`. Любой формат «на экспорт наружу» обязан нести `schemaVersion` и миграции.

**Следствия.** Обратная совместимость экспортов/шарингов; storage-миграции и сериализация используют общий подход. Требование зафиксировать `schemaVersion` для каждого нового kind — часть Definition of Done соответствующих фич.

## ADR-0017: Разделение tsconfig (app/node) и охват type-aware ESLint
**Статус:** Accepted · **Дата:** 2026-09-01

**Контекст.** Черновая конфигурация TASK-001 предполагала один `tsconfig.json`, включающий и `src`, и конфиги инструментов (`vite.config.ts`, `vitest.config.ts`, `eslint.config.js`), плюс `references` на `tsconfig.node.json`. На практике это ломается: (1) `references` требует `composite`, несовместимого с `noEmit` (`TS6310`); (2) конфиги инструментов используют Node-глобалы (`import.meta.dirname`, `process`) и не должны компилироваться с `types: ["chrome"]`/DOM app-проекта; (3) type-aware ESLint через `projectService` привязывает каждый файл к ближайшему `tsconfig.json` — корневые конфиги не попадают в `include` app-tsconfig и дают parsing error.

**Решение.**
- Два независимых проекта: `tsconfig.json` (`include: ["src"]`, DOM+chrome типы) и `tsconfig.node.json` (конфиги инструментов + `scripts/**`, `types: ["node"]`). Оба `noEmit`, без `references`.
- `pnpm typecheck` = `tsc --noEmit && tsc --noEmit -p tsconfig.node.json` — покрывает оба проекта.
- ESLint: type-aware наборы (`strictTypeChecked`+`stylisticTypeChecked`) применяются только к `src/**/*.{ts,tsx}` через `projectService`. Тулинг/конфиг-файлы обслуживаются отдельным блоком (`disableTypeChecked`, `parser: tseslint.parser`, `project: false`) — типы им проверяет `tsc` по `tsconfig.node.json`.

**Следствия.** Границы «код приложения» и «тулинг» явные; фичам первой волны и далее исходники живут только под app-tsconfig. Любой новый конфиг/скрипт добавляется в `include` `tsconfig.node.json`. Минус: два вызова `tsc` в typecheck (незначительно).

**Альтернативы.** `composite` + `tsc -b` (отвергнут: конфиг-проект вынужденно эмитит `.d.ts` ради ссылок); `projectService.allowDefaultProject` для конфигов (отвергнут: хрупкий whitelist, конфликт с `include`).

## ADR-0018: Тестовый харнес — пороги покрытия и границы гейта (TASK-011)

**Статус:** Accepted · **Дата:** 2026-09-03

**Контекст.** TASK-011 требует QA-гейты: пороги покрытия как реальный блокер CI, e2e поверх собранного MV3-расширения, a11y-smoke. Спека называет ориентиры «≥80% core, `logic.ts` ~95%, `shared/**` ~90%». При замере на фактической кодовой базе выяснилось: **statements/functions/lines** по чистой логике уже 96–100%, но **branch-покрытие** систематически ниже (71–91% в `logic.ts`, 60–88% в `shared/**`). Остаток ветвления — это защитные `?? default` (правые части nullish на всегда-определённых ключах `Intl.formatToParts`/индексах типизированных массивов) и `catch`-и на непроходимых путях (`TextEncoder`/`JSON.stringify` разобранного значения не бросают). Догнать их до 95% можно только искусственными тестами/фейками, что вредит сигналу. Дополнительно `src/shared/messaging/transports.ts` — платформенный chrome-seam (граница ADR-0014): его ветки — реальная передача сообщений, юнит-тестируется слабо, покрывается e2e.

**Решение.**
- **Пороги (реальный гейт, ненулевой exit при падении):** общий floor 80/80/80/80 (канон PRD §12). Per-path override: `src/features/**/logic.ts` — **95** по statements/functions/lines (содержательный high-bar «core почти 100%»), branch — **enforced floor 68**; `src/shared/**` — 88/82/88 по statements/functions/lines, branch floor 55. Branch-пороги — намеренно floor, а не 95/90: гейтить защитные/непроходимые ветки бессмысленно; регресс ловится по строкам/функциям.
- **Среда unit — jsdom** (не happy-dom из черновика спеки): существующий сюит (404 теста) зелёный на jsdom; смена среды — churn без функционального выигрыша. `happy-dom` не добавлялся (неиспользуемая зависимость).
- **Третий tsconfig — `tsconfig.test.json`** (расширяет разделение из ADR-0017): охватывает `tests/**` + `playwright.config.ts`, `types: ["node","chrome","vite/client"]`. `pnpm typecheck` теперь = три `tsc --noEmit`. ESLint для `tests/**` — отдельный `disableTypeChecked`-блок (типы проверяет tsc).
- **chrome.\*-мок** (`tests/mocks/chrome.ts`) — минимальный, но stateful: `storage.local` держит реальный in-memory объект (иначе тесты сохранённых под-вкладок не работают), методы dual-mode (promise+callback для `webextension-polyfill`).
- **e2e** — persistent context с `--load-extension`, `extensionId` из URL MV3 service worker; рабочий режим headed (в CI под xvfb) либо `--headless=new`. `global-setup.ts` падает рано, если `dist/` не собран.

**Следствия.** Гейт зелёный и осмысленный: 404 unit + порог покрытия, 4 e2e (popup+sidepanel, декодер end-to-end, a11y без serious/critical). Branch-floor задокументирован как политика — поднимать пороги можно по мере роста тестов, но не искусственными кейсами. Минус: три вызова `tsc`; branch-floor визуально ниже канона (компенсируется высоким statements/functions/lines и e2e-покрытием seam). Поднятие `shared/**` до 90 по строкам и покрытие `transports.ts`/reject-ветки `useSettings` — в бэклоге (TASK-020/уточнить), не блокирует.

**Альтернативы.** (1) Пороги 95/90 по всем метрикам с массой `/* v8 ignore */` на защитных ветках — отвергнут: захламляет исходники фич аннотациями, смещает работу TASK-011 в чужой scope. (2) Догон branch искусственными тестами — отвергнут: ложный сигнал качества. (3) happy-dom по умолчанию — отвергнут: риск регресса зелёного сюита без выигрыша.

## ADR-0019: CI/CD — единый источник версии и релиз по тегу (TASK-012)

**Статус:** Accepted · **Дата:** 2026-09-03

**Контекст.** TASK-012 требует GitHub Actions (PR-гейт + релиз), версионирование через changesets, синхронизацию `package.json` ↔ `manifest.json`, упаковку zip. Спека перечисляет скрипты `sync-manifest-version.mjs` и `zip.mjs`. Но архитектура манифеста (TASK-002) устроена иначе: `src/manifest.config.ts` генерирует манифест **из** `package.json` при сборке (`version` нормализуется `toExtensionVersion`, полный semver — в `version_name`); статичного `manifest.json` в репозитории нет. Скрипт упаковки (`scripts/package.mjs`) уже существует с TASK-002.

**Решение.**
- **Единый источник версии — `package.json`.** Синхронизация с манифестом **автоматическая** (генерация при сборке), поэтому отдельный `sync-manifest-version.mjs` не создаётся — вместо записи файлов CI **проверяет** соответствие: `scripts/check-version.mjs` сверяет тег ↔ `package.json` ↔ собранный `dist/manifest.json` (`version`+`version_name`), ненулевой exit при рассинхроне.
- **Упаковка — переиспользуем `scripts/package.mjs`** (`pnpm run package` → `dist-zip/qaid-<version>.zip`, без source maps), а не дублируем как `zip.mjs`.
- **Workflow'ы:** `ci.yml` (PR+push main): job `quality` (install→typecheck→lint→format:check→test:coverage→build, артефакты coverage/dist) + job `commitlint` (заголовки коммитов PR). `e2e.yml`: Playwright под `xvfb` — **временно non-blocking** (гоняется, но не в required checks, пока стабилизируется). `release.yml`: на push main — Version PR через `changesets/action`; на тег `v*.*.*` — гейт→build→check-version→package→`release-notes.mjs`→**draft** GitHub Release с zip.
- **Версионирование — @changesets/cli** (`.changeset/config.json`, single private package). Поток: changeset в PR → Version PR бампит `package.json`+`CHANGELOG.md` → merge → тег → релиз.
- **Безопасность:** `permissions: contents: read` по умолчанию, повышение точечно на job (Release — `contents: write`, Version PR — `pull-requests: write`). Ядро CI без секретов (ADR-0007); CWS-секреты — только в job `release`, заготовка upload за TODO. `Dependabot` для `npm`+`github-actions`. Actions закреплены по мажорным тегам (SHA-pin — как опция усиления).

**Следствия.** Версия ведётся в одном месте, рассинхрон невозможен незаметно (CI-гейт). Меньше кода (нет двух cargo-cult скриптов). Релиз — draft (человек публикует). Живой прогон CI не проверить локально (нет remote) — валидировано статически (YAML-парс, локальный прогон `check-version`/`release-notes`/`package`, changeset-config читается). Минус: e2e пока не required — зафиксирован план сделать blocking (RELEASING.md). Ограничение: `check-version.mjs` дублирует нормализацию `toExtensionVersion` (Node ESM не импортирует TS) — 12 строк, покрыты сверкой на реальном артефакте.

**Альтернативы.** (1) `sync-manifest-version.mjs`, пишущий `manifest.json` — отвергнут: нет статичного манифеста, скрипт был бы no-op. (2) `zip.mjs` — отвергнут: дублирует `package.mjs`. (3) Публикация в CWS сразу — отвергнута (спека §Вне scope): на старте zip+draft, upload позже с секретами.

## ADR-0020: Инъекция инспектора — динамическая (`chrome.scripting`) + отдельный IIFE-бандл

**Статус:** Accepted · **Дата:** 2026-09-03

**Контекст.** Инспекционному слою (TASK-013) нужен content-скрипт в активной вкладке: мост «UI → content» и доступ к DOM. Два вопроса: (1) статические `content_scripts` в манифесте vs инъекция по требованию; (2) как под сборкой @crxjs получить инъектируемый артефакт.

**Решение.**
- **Динамическая инъекция, не статические `content_scripts`.** Скрипт инъектируется `chrome.scripting.executeScript` при первом запуске инструмента (least-privilege, ADR-0013): не грузимся на каждой странице у каждого пользователя; доступ — только когда QA осознанно запустил инспектор, и только к целевой вкладке (`activeTab`). Идемпотентность — guard-флаг `window.__qatb_inspection__` в content-хосте: повторная инъекция не плодит слушатели.
- **Отдельный IIFE-бандл `dist/content-inspection.js`** (`scripts/build-content.mjs`, шаг `pnpm build`). Причина: `executeScript({ files })` грузит файл как классический (не-module) скрипт — он обязан быть самодостаточным IIFE без внешних import'ов. @crxjs выдаёт ESM-чанки с хешированными путями (для module-энтрипойнтов), что для такой инъекции непригодно, а `.ts` в `web_accessible_resources` @crxjs копирует как сырой исходник. Поэтому хост собирается отдельным `vite build` в IIFE со стабильным именем (= константе `INSPECTION_CONTENT_SCRIPT`). WAR не нужен: Chrome не требует web-accessible-декларации для файлов `executeScript`.
- **Триггер инъекции — уровень сообщения (`target: 'content'`), а не флаг фичи.** `defineMessage(..., { target: 'content' })` помечает запросы, адресованные вкладке; background генерически (`installInspectionForwarding`) для таких типов делает `ensureContentScript` + форвард в вкладку — конкретные `inspection/*` в ядре не упоминаются (инвариант расширяемости). Дескриптор `FeatureModule.content: { world, injectOn }` остаётся декларацией контракта инъекции фичи и **нагружен** fitness-инвариантом (§12.6): фича с content-адресованными сообщениями обязана его декларировать.

**Следствия.** Права запрашиваются точечно и по требованию; content-бандл (~58 KB, включает zod для валидации на границе) грузится только при использовании инспектора. Минус: отдельный шаг сборки content-хоста (встроен в `build`); дублирование имени файла между `build-content.mjs` и константой в background (одна строка, покрыта e2e-инъекцией). Реальную инъекцию нельзя достоверно подтвердить в jsdom/CI без гранта host-доступа (`activeTab` даётся лишь по action-инвокации на вкладке) — покрывается юнитами (менеджер инъекции, хост, пикер, форвардинг) + e2e на Load unpacked (см. PROGRESS).

**Альтернативы.** (1) Статические `content_scripts` — отвергнуто: грузится на всех страницах, ломает least-privilege. (2) `.ts` в `web_accessible_resources` + динамический `import(getURL())` — отвергнуто: @crxjs копирует сырой TS, а хешированный ESM-чанк не имеет стабильного пути. (3) ESM-бандл через `rollupOptions.input` — отвергнуто: `executeScript files` не резолвит import'ы в контексте страницы.

## ADR-0021: Оверлей инспектора — Shadow DOM в `closed` режиме

**Статус:** Accepted · **Дата:** 2026-09-03

**Контекст.** Инспектор рисует подсветку элементов и UI пикера поверх страницы. Требования: не мутировать DOM/стили страницы (иначе ломаем то, что тестирует QA), не протекать стилями страницы в оверлей и наоборот, устойчивость к строгому CSP.

**Решение.** Единый host-элемент с `attachShadow({ mode: 'closed' })`; внутри — reset-обёртка `all: initial` и программно созданные inline-стилизованные узлы (без внешних ресурсов/`eval` — CSP-safe). Host: `position: fixed; inset: 0; pointer-events: none; z-index: 2147483647` — оверлеит, но пропускает клики; подсветка — `pointer-events: none`. Host помечен `data-qatb-overlay`, чтобы обходы DOM (`walk`) и пикер исключали себя. Полный teardown по `inspection/teardown` и `pagehide`. `closed`-режим — чтобы страница не могла достучаться до `shadowRoot` оверлея.

**Следствия.** Стили страницы и оверлея изолированы; DOM страницы вне оверлея не изменяется (проверяется e2e-снимком до/после). Пикер использует `event.target` (не `elementFromPoint`) — робастно при `pointer-events: none` и тестируемо в jsdom. Ограничение при очень строгом CSP: только программные узлы и inline-стили в Shadow DOM (задокументировано); внешние ресурсы/шрифты в оверлей не тянем.

## ADR-0022: Host-доступ инспектора — постоянный optional host вместо `activeTab`

**Статус:** Accepted · **Дата:** 2026-09-04

**Контекст.** Инспектор живёт в side panel и инъектирует content-хост в целевую
вкладку (ADR-0020). Изначально host-доступ давал `activeTab` (least-privilege,
точечно вместо `<all_urls>`). Но `activeTab` предоставляет доступ **только к
вкладке, активной в момент инвокации расширения** (открытия панели через action), и
**не** распространяется на вкладки, куда пользователь переключается позже. Для side
panel, которая переживает смену вкладок, это давало устойчивый баг: открыв панель на
одной вкладке (в т.ч. служебной `chrome://`), пользователь переходил на обычную
страницу — и инъекция падала с «Cannot access contents of the page. Extension
manifest must request permission to access the respective host.». Инструмент
«залипал» до переоткрытия панели (переоткрытие = новая action-инвокация на текущей
вкладке = новый `activeTab`-грант).

**Решение.** Заменить `activeTab` на **постоянный optional host-грант** `*://*/*`
(`optional_host_permissions`), запрашиваемый брокером под пользовательским жестом при
первом запуске инспектора вместе со `scripting`. Постоянный грант не привязан к
инвокации и переживает переключение вкладок — инъекция работает на любой обычной
вкладке независимо от того, где была открыта панель. `scripting` остаётся в
`optional_permissions`.

Почему не per-origin (least-privilege по домену). MV3 требует, чтобы
`permissions.request` вызывался синхронно в пользовательском жесте. Чтобы запросить
конкретный origin, нужно сперва прочитать URL активной вкладки (право `tabs` или уже
имеющийся host-доступ), а это асинхронно — после `await` жест «сгорает», и
последующий `request({ origins })` браузер отклонит. Значит, надёжный per-origin в
одном жесте невозможен; он потребовал бы права `tabs` и двухшагового согласия на
каждый новый домен. Для инспектора произвольных страниц постоянный host — прагматично
корректный и предсказуемый выбор при разовом согласии.

**Следствия.** Инспектор надёжно следует за активной вкладкой; баг «залипания» при
смене вкладки устранён на уровне модели прав, а не симптоматически. Служебные
страницы (`chrome://`, магазин, `view-source`) остаются недоступными по политике
браузера и обрабатываются мягко (`PRIVILEGED_PAGE`, понятное сообщение,
инструмент остаётся рабочим). Классификатор ошибок инъекции упорядочен так, чтобы
нехватка host-доступа давала `PERMISSION_DENIED` (чинится грантом), а не
`PRIVILEGED_PAGE`. Цена — более широкий разовый запрос («доступ ко всем сайтам»)
вместо точечного `activeTab`; область — http/https (`file://` требует отдельного
тумблера в настройках расширения и вне зоны инспектора). Приватность не страдает:
ядро не делает внешних сетевых вызовов, содержимое страницы уходит только в UI
расширения.

**Альтернативы.** (1) `activeTab` — отвергнуто: не переживает смену вкладок (корень
бага). (2) Per-origin host + `tabs` — отвергнуто: невозможно в одном жесте, плюс
право `tabs` и худший UX (диалог на каждый домен). (3) Привязать инспектор к вкладке
инвокации — отвергнуто: формализует ту самую боль (инспектор не следует за вкладкой).

## ADR-0023: Инспекционный слой — страничный `scan`, генерический `highlight`, async-сборщики

**Статус:** Accepted · **Дата:** 2026-09-04

**Контекст.** TASK-013 дал слой с моделью «выбрать элемент пикером → `collect`
сборщиком на этом якоре». Первые реальные инспекторы (контраст/палитра/шрифты,
TASK-014…016) сканируют **всю страницу**, а не один узел, и хотят «клик по нарушению
→ показать узел на странице». Гнать это через `pick`+`collect` неудобно (скан без
якоря невозможен), а переносить DOM-ссылки через границу сред нельзя (сериализуемость).
Плюс сбор шрифтов асинхронен (`document.fonts`), а `collect` не дожидался промиса
сборщика (данные ушли бы как `Promise`).

**Решение.** Три аддитивных, обратно совместимых расширения слоя (контракты — в
`shared/inspection`, реализация — в content-хосте):
1. **`inspection/scan { inspectorId }`** — прогон именованного сборщика по всей
   странице (корень — `document.body`; оверлей висит на `<html>`, вне обхода). Не
   требует якоря — основной путь страничных инспекторов. `pick`+`collect` остаётся для
   режима осмотра одного узла (eyedropper).
2. **`inspection/highlight { selector }`** — генерическая, без состояния подсветка:
   хост находит `querySelector`, скроллит к узлу и рисует рамку в оверлее. Инспекторы
   отдают в UI сериализуемый `selector` на пункт и подсвечивают узел, не таская
   DOM-ссылки через границу. Невалидный/ненайденный селектор → `{ found:false }`, без
   краха.
3. **Async-сборщики.** `collect`/`scan` дожидаются сборщика (`Promise.resolve(...).then`),
   сохраняя синхронный `throw` валидации («нет якоря»/«нет сборщика») до промиса —
   роутер получает `AppErrorException` тем же путём, что и раньше.

**Следствия.** Страничные инспекторы строятся на слое без его форка: сборщик —
чистая `(root) => сериализуемые данные`, запускаемая и на `body` (скан), и на якоре
(осмотр). Подсветка переиспользуема всеми инспекторами. `scrollIntoView`
вызывается по наличию (нет в jsdom/эмбедах) — тестируемо и безопасно. Риск:
`highlight` по одиночному селектору best-effort (селектор может быть неуникален) —
приемлемо для MVP, узел не найден → тихий no-op. Инвариант расширяемости сохранён:
ядро не упоминает конкретные `inspection/*`, background форвардит их генерически.

**Альтернативы.** (1) Скан через обязательный `pick` якоря — отвергнуто: лишний шаг и
неверная семантика для страничного инструмента. (2) Возврат DOM-ссылок/индексов узлов
в UI для подсветки — отвергнуто: несериализуемо и требует состояния соответствия на
хосте; селектор проще и без состояния. (3) Отдельные доменные сообщения на каждый
инспектор — отвергнуто: дублирование; один общий `scan`/`highlight` покрывает всех.

## ADR-0024: R1.1-кластер #2 — storage/cookies, линейка, формы поверх слоя; двухканальный storage; a11y-токен подписи

**Статус:** Accepted · **Дата:** 2026-09-04

**Контекст.** Второй кластер R1.1 (TASK-017 storage/cookies, TASK-018 линейка,
TASK-020 формы) строится на инспекционном слое (TASK-013) и распараллелен тремя
субагентами. Нужно было развести три новые фичи без гонок за общие файлы, а также
решить: как редактировать cookies (недоступны из JS страницы), куда класть доменные
и content-модули, чтобы не нарушить fitness §12.1 (ядро/бандл не импортят фичи), и как
провести новые content-мутации (`storage/*`, `forms/*`) через существующий хост.

**Решение.**
1. **Двухканальный storage-редактор (TASK-017).** `localStorage`/`sessionStorage` —
   через content-мост (RPC `storage/list|set|remove|clear`, `target: 'content'`,
   ISOLATED-мир активной вкладки). **Cookies** — через background-хендлеры
   (`cookies/*`, `target: 'background'`) поверх `chrome.cookies` (новый platform-seam
   `cookies` + `tabs.getUrl` для сборки `url`). Мотив: `chrome.cookies` даёт правку
   `HttpOnly` (недоступно чистому JS) — заметный дифференциатор против DevTools; а
   `chrome.cookies.set` требует корректный `url` (secure+domain+path), собираемый
   чистым `buildCookieUrl`.
2. **Доменные и content-модули — в `shared/inspection/<name>/`, не в `features/`**
   (как ADR-0023): content-бандл импортит их, а импортировать `@/features/*` ему
   запрещено (fitness §12.1). Фича-каталог держит только UI-поверхность
   (ui/settings/i18n/index). Генераторы форм тянут `@/shared/random` напрямую (не
   `@/features/random-*` — тот же инвариант); вынос общего `shared/test-data` — в бэклоге.
3. **Проводка content-мутаций — генерическая.** Новые `target:'content'` типы
   автоматически форвардятся background'ом (`installInspectionForwarding` читает
   `contentMessageTypes()` из реестра — правки фона не нужны). Их хендлеры регистрируются
   в общей шине из `content/inspection/index.ts` (`installStorageContentHost`/
   `installFormsContentHost`) до `installInspectionHost()` (роутер один, lookup ленивый).
   `backgroundHandlers` cookies подключаются ядром генерически из дескриптора фичи.
4. **Категории `environment`/`forms`** добавлены в `FeatureCategory` (расширяемая точка
   ядра) + i18n-метки. `storage` уже существовала.
5. **A11y-токен `--fg-caption`.** Метка категории активного инструмента в оболочке
   редизайна использовала `--faint` (zinc-400, 2.37:1 на светлой поверхности) — провал
   WCAG AA для несущего текста (поймано axe в e2e). Введён семантический токен
   `--fg-caption` (светлая: новый zinc-600 = 7.16:1; тёмная: переиспользован
   светло-серый muted), чтобы `--faint` остался для декоративных подписей/плейсхолдеров/
   глифов, а несущие подписи держали AA. Точечно, без сдвига тона `--fg-muted`.
6. **E2e под оболочку редизайна.** Незакоммиченный редизайн заменил «стек всех панелей»
   на **одну активную панель + рельс/strip**. Рендер-спеки (пред-существующие
   контраст/шрифты/палитра/инспектор/popup **и** новые) переведены на навигацию: клик по
   кнопке рельса (aria-label = заголовок фичи) → ассерт действия в активной панели. Это
   было пред-существующее падение e2e от редизайна, не от фич кластера.

**Следствия.** Три фичи легли без файловых конфликтов (субагенты — строго свои каталоги;
оркестратор — общие: барель, content-index, манифест, категории, платформа, доки, гейты).
`HttpOnly`-правка cookies работает и покрыта e2e (background-хендлер). Свободная линейка
(drag+snap, часть scope TASK-018) требует интерактивного инструмента поверх оверлея хоста
— вынесена в бэклог (TASK-033), поставлены A/B-измерение и box-model. Право `cookies` —
optional, запрашивается под жестом при открытии cookies-вкладки; отказ не роняет фичу
(storage-вкладки работают). Инвариант расширяемости сохранён: ядро не упоминает конкретные
`storage/*`/`forms/*`/фичи.

**Альтернативы.** (1) Cookies через content-скрипт — отвергнуто: JS страницы не видит
`HttpOnly` и не пишет его. (2) Доменные модули в `features/` — отвергнуто: ломает
fitness §12.1 (content-бандл потянул бы фичу). (3) Отдельный background-форвардинг на
каждый content-тип — отвергнуто: уже генерический из реестра. (4) Затемнить `--fg-muted`
глобально — отвергнуто: сдвинул бы тон всей вторичной типографики редизайна; точечный
`--fg-caption` минимальнее. (5) Оставить e2e-спеки на «стек панелей» — отвергнуто: они
уже красные от редизайна; привели к фактической навигации оболочки.

## ADR-0025: Единый каталог фич на обеих поверхностях — `surface: 'both'` + `requiresPanel` вместо surface-разбиения

**Статус:** Accepted · **Дата:** 2026-09-04

**Контекст.** Каталог фич расходился по поверхностям: генераторы и декодеры были
`surface: 'popup'` (видны только в strip popup), а инспекторы/storage/формы —
`surface: 'sidepanel'` (видны только в рельсе side panel). Итог: пользователь видел
разный набор инструментов в popup и в side panel, а `getFeatures('popup')` вообще не
пускал «панельные» инструменты в strip — их нельзя было даже обнаружить из popup.
Требовалась синхронизация: все фичи доступны на обеих поверхностях, но без деградации
UX там, где инструмент физически не может работать в transient-popup.

**Ключевое ограничение платформы.** MV3-popup закрывается при потере фокуса — в т.ч.
при клике по странице. Поэтому инструменты с **живым захватом элементов** (пикер
элемента `inspector-probe`, захват точек A/B `inspector-ruler`) в popup
принципиально нерабочие: клик по странице для выбора закрывает popup до завершения
пика. Сканеры (контраст/палитра/шрифты), storage/cookies и формы работают
**программно** (скан/чтение-запись активной вкладки без клика по странице) — им popup
подходит.

**Решение.**
1. **Все фичи — `surface: 'both'`.** `getFeatures('popup')` и `getFeatures('sidepanel')`
   теперь возвращают один и тот же набор → strip popup и рельс side panel
   синхронны. Поле `Surface` и `getFeatures` не меняются (семантика «где инструмент
   перечислен»), меняются только дескрипторы фич.
2. **Новый флаг `requiresPanel?: boolean`** в `FeatureModule` — «инструменту нужна
   персистентная поверхность (живой пик)». Отделяет *доступность в списках* (`surface`)
   от *возможности рендера в popup*. Проставлен только пикерам (`inspector-probe`,
   `inspector-ruler`).
3. **Popup чтит `requiresPanel`.** `renderableInPopup` в `PopupShell` теперь проверяет
   `f.requiresPanel !== true` (а не `surface`). Пикеры остаются в strip popup
   (обнаружимы, кликабельны), но вместо сломанного UI рендерят существующий fallback
   `shell.openInPanel` с кнопкой открытия side panel (жест → `sidePanel.open`). Копия
   fallback уточнена: объясняет, что пик работает только в панели (popup закрывается
   при клике по странице).
4. **Единая сквозная нумерация `order`** (шаг 10, сгруппировано по категориям:
   генераторы 10–20, утилиты/декодеры 30–40, инспекторы 50–90, storage 100, формы 110)
   — обе поверхности читаются одинаково, без чересстрочных коллизий порядков.

**Следствия.** Паритет поверхностей: любой инструмент доступен и из popup, и из side
panel, а палитра (⌘K) и так знала про все. Инвариант расширяемости сохранён — ядро не
упоминает конкретные фичи; новая фича сама решает `surface`/`requiresPanel`. Layout
выдерживает рост числа кнопок: `.strip` уже `overflow-x:auto`, `.rail` — `overflow-y:auto`
(кнопки `flex:none`, контейнер скроллится). E2e-покрытие: сканер рендерит реальный UI в
popup; пикер в popup показывает fallback (оба теста зелёные). Пред-существующая
флакость permission-gated e2e (нативный диалог `permissions.request` под синтетическим
жестом недетерминированно вешает инъекцию/RPC до 30s — воспроизводится и на нетронутом
`inspection.spec.ts:42`) — вне scope этой правки; детерминированный e2e подтверждается на
load-unpacked (ADR-0020/0022).

**Альтернативы.** (1) Оставить surface-разбиение — отвергнуто: не выполняет требование
паритета, «панельные» инструменты недостижимы из popup. (2) Всё `both` без
`requiresPanel` — отвергнуто: пикеры в popup сломаны (клик по странице закрывает popup),
не prod-ready. (3) Отдельная поверхность-флаг на «тяжесть» через `surface: 'sidepanel'`
+ показ в popup через ad-hoc список — отвергнуто: смешивает доступность и рендер;
`requiresPanel` — явная, единичная точка. (4) Хардкод списка «панельных» id в
`PopupShell` — отвергнуто: ломает инвариант расширяемости (ядро знало бы фичи).

## ADR-0026: Эмуляция окружения — MAIN-world оверрайды через `executeScript({func})` + DNR session-rules; честное ограничение TZ
**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-019 требует подменять окружение активной вкладки в двух разных
плоскостях: заголовки запроса (`User-Agent`/`Accept-Language`) — на сетевом уровне, и
JS-API страницы (`navigator.userAgent`/`language(s)`, `navigator.geolocation`,
`Intl`/`Date` таймзона) — в контексте самой страницы. Только заголовок оставит JS-детект
настоящим (типичная ловушка), только JS-подмена не затронет реальные запросы. До TASK-019
в проекте не было **ни** DNR, **ни** MAIN-world инъекции — весь инспекционный слой
(TASK-013) живёт в ISOLATED-мире через собранный IIFE `content-inspection.js`.

**Решение.**
1. **Заголовки — `chrome.declarativeNetRequest` session-rules**, ограниченные `tabId`
   (`updateSessionRules`). Право декларируется **install-time как
   `declarativeNetRequestWithHostAccess`**, а НЕ в `optional_permissions`: Chrome
   запрещает `declarativeNetRequest*` быть optional (молча отбрасывает, после чего
   рантайм-`permissions.request` падает с «Only permissions specified in the manifest may
   be requested»). Взята host-гейтная разновидность — её правила действуют только на
   origin'ы с host-доступом, поэтому сам API-грант не даёт наблюдаемого доступа и не
   поднимает широкого install-warning; чувствительная часть (host `*://*/*`) остаётся
   optional и запрашивается брокером под жестом при мастер-тумблере (фича opt-in по
   факту). Session-rules эфемерны (сбрасываются при перезапуске SW) и снимаются при
   выключении/закрытии вкладки — **никаких персистентных правил** (least-privilege).
2. **JS-API — MAIN-world инъекция чистой функции через `executeScript({ world: 'MAIN',
   func, args })`**, а НЕ отдельный IIFE-бандл, как у ISOLATED-хоста. Конфиг передаётся
   аргументом (Chrome сериализует `func.toString()` + args), поэтому не нужны ни второй
   бандл в `build-content.mjs`, ни relay для доставки конфига. Требование —
   самодостаточность инъектируемых функций (`overrides.ts`): только аргумент + глобалы
   страницы, состояние/undo — на `window.__qatbEnvOverrides__`.
3. **Оркестрация — в background** (`environment/apply` · `environment/clear`,
   `backgroundHandlers`), а не content-target: DNR и `executeScript` доступны только из
   SW. Фон держит in-memory реестр активных вкладок и **ре-инъектирует** MAIN-оверрайды на
   `tabs.onUpdated{status:'loading'}` (инъекция не переживает навигацию; DNR-заголовки —
   переживают сами), снимает правила на `tabs.onRemoved`. `chrome.*` — только в
   платформенном seam (`declarativeNetRequest`/`scriptingMain`/`tabEvents`), фича ходит
   через него (fitness §5).
4. **Категория `environment`** уже была в `FeatureCategory`; UI-вкладок категорий нет
   (ярлык рендерится из i18n) — фича лишь регистрируется с `category: 'environment'`.

**Следствия.** UA/язык подменяются и в заголовке, и в JS; геолокация перехватывается с
режимом «ошибка» для тестирования ветвей. **Честное ограничение (задокументировано):**
полноценный TZ-override на уровне движка `Date` без CDP невозможен — покрываем
`Intl.DateTimeFormat` и `Date.prototype.getTimezoneOffset`, чего хватает большинству
web-сценариев; CDP-режим — опциональное улучшение следующей волны. MAIN-инъекция
применяется к текущему документу и ре-инъектируется при навигации, но до первых скриптов
страницы успевает не всегда (`injectImmediately`) — для гарантии на load рекомендуется
перезагрузка. Чистая логика (валидация, сборка DNR-правил, query-мердж) вынесена в
`logic.ts` (~100% покрытие); `overrides.ts`/`background.ts` — тонкие исполнители.

**Альтернативы.** (1) Отдельный IIFE-бандл `environment-main.js` + relay для конфига (как
ISOLATED-хост) — отвергнуто: `func`-инъекция проще, без новой сборки и канала доставки
конфига. (2) Только заголовки (DNR) без MAIN-подмены — отвергнуто: JS-детект видел бы
настоящий UA. (3) Персистентные DNR-правила — отвергнуто: грязное состояние между
сессиями, нарушает least-privilege. (4) CDP (`chrome.debugger`) для полной TZ/девайс-
эмуляции — отложено: тяжёлое право и UX «расширение отлаживает вкладку», вне MVP.

## ADR-0027: Гибридная стратегия перехвата сети — MAIN-инъекция по умолчанию, CDP опционально
**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-022 (мок сети) — ядро ценности R2. PRD §9 фиксирует гибридную
стратегию перехвата: инъекция-обёртка `fetch`/XHR в MAIN-world (без баннера отладки,
но не ловит обходящие запросы и ломается на строгом CSP) либо CDP-режим
(`chrome.debugger`) — полный контроль, но баннер «расширение отлаживает вкладку» и
тяжёлое право. Нужно доставить рабочий путь, не завязываясь на тяжёлый CDP.

**Решение.** MAIN-инъекция — дефолт и единственный реализованный путь v1; CDP —
контракт-задел (стратегия `cdp` в UI/сообщениях возвращает `ok:false` +
`reason:'cdp-not-implemented'`), полная реализация вынесена в бэклог (TASK-032).
Перехватчик — самодостаточная функция, инъектируемая через `scriptingMain`
(как `environment/overrides`, ADR-0026), живёт в **фиче** `features/mock-network`
(не в `src/page/` и не в content-бандле): код вне фичи не смеет импортировать
конкретную фичу (fitness §12.1), а перехватчику нужны её типы. Правила
**компилируются** тестируемой чистой `logic.ts` (glob→ReDoS-безопасный regex source с
анкорингом/экранированием) ДО инъекции; перехватчик получает готовый `source`+`flags`
и лишь строит `new RegExp(...).test(url)` — «опасная» часть не дублируется в
инъектируемой функции. Живой список — опрос лога (`mock/poll` → `scriptingMain`), а не
постоянный канал: проще, без relay, достаточно для v1.

**Следствия.** Плюсы: рабочий мок без тяжёлого права `debugger`, без баннера,
переживает навигацию (ре-инъекция по `tabEvents`, как environment); чистая логика на
100% тестируема на «запрос-объектах». Минусы/честные ограничения (документированы):
не ловит запросы в обход `window.fetch`/XHR (Beacon/worker-fetch), ломается на строгом
CSP, блокирующем MAIN-инъекцию (→ предложить CDP-режим), passthrough-мутация тела
реального **XHR** вне v1 (fetch — основной путь). fail-open: любая ошибка правила →
реальный запрос идёт как есть, мок не роняет тестируемую страницу. Приватность:
перехваченные тела/заголовки не покидают страницу иначе как в снимок лога, забираемый
только своей панелью. Прав сверх `scripting`+host (уже optional с TASK-013) не
вводится; `debugger` появится вместе с TASK-032.

**Альтернативы.** (1) Сразу CDP — отвергнуто: тяжёлое право, баннер, больше объём, вне
MVP-ценности. (2) Перехватчик в `src/page/` как отдельный MAIN-бандл — отвергнуто:
нарушал бы fitness §12.1 (импорт типов фичи вне фичи) и требовал второй сборки; func-
инъекция из фичи проще и однородна с environment. (3) Постоянный канал MAIN↔panel
через relay вместо опроса — отложено: сложнее, для живого списка v1 опрос достаточен.

## ADR-0028: MAIN-инъектируемые функции обязаны быть самодостаточными; guard `reserialize`
**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** `chrome.scripting.executeScript({ world: 'MAIN', func })` сериализует
переданную функцию как `func.toString()` и исполняет её в контексте страницы **без
замыкания модуля**, из которого она пришла. Любая ссылка в теле на биндинг уровня
модуля (константа, хелпер, импорт-значение) после сборки становится свободным
идентификатором (минификатор переименовывает, напр. `STORE_KEY`→`Dn`) и падает
`ReferenceError` на странице. Оба MAIN-канала — перехватчик мока
([interceptor.ts](../src/features/mock-network/interceptor.ts), TASK-022) и оверрайды
окружения ([overrides.ts](../src/features/environment/overrides.ts), TASK-019) — вынесли
строковый ключ состояния (`__qatbMock__` / `__qatbEnvOverrides__`) в **модульную**
константу. В рантайме это означало: инъекция молча падала, `window.__qatbMock__` не
создавался, `mock/poll` всегда возвращал `[]` → **список запросов не наполнялся при
бейдже «active»**; эмуляция окружения не применялась. Юнит-тесты дефект не ловили: они
дергают функции **напрямую в области модуля**, где константа доступна; сквозной путь
(сериализация в страницу) прикрыт soft-skip в e2e.

**Решение.** (1) Инвариант: **всякая MAIN-инъектируемая функция самодостаточна** —
использует только свой аргумент и глобалы страницы; любые нужные ей константы/хелперы
объявляются **внутри тела**. Ключи состояния перенесены внутрь каждой из injected-
функций (install/clear/read у мока; apply/clear у окружения). (2) Регрессионный guard:
тест-хелпер [`reserialize`](../tests/support/reserialize.ts) реконструирует функцию из
её `.toString()` через `new Function` (чистая область, как MAIN-world) и прогоняет
полный цикл (`install→fetch→readLog→clear`, `apply→restore`). Утечка модульного
биндинга → `ReferenceError` → красный тест. Guard'ы:
[mock](../src/features/mock-network/__tests__/serialization.test.ts),
[environment](../src/features/environment/__tests__/serialization.test.ts).

**Следствия.** Плюсы: мок и эмуляция реально работают на странице; класс бага закрыт
воспроизводящим тестом, а не одной правкой символа; контракт самодостаточности из
docstring'ов обеих фич теперь **проверяется**, а не только декларируется. Обязательно:
новые MAIN-инъекции сопровождаются `reserialize`-тестом. Минус: короткое осознанное
дублирование строкового литерала ключа внутри функций (drift пинится теми же guard'ами
— при рассинхроне ключей read вернёт `[]`).

**Альтернативы.** (1) Прокидывать ключ через `args` (единый источник в types.ts) —
отвергнуто: больше церемоний в сигнатурах clear/read, а инлайн-литерал + guard решают
DRY-риск дешевле. (2) Не выносить константу вовсе (оставить как было) — и был баг.
(3) Только починить символ без теста — отвергнуто: класс бага молча вернулся бы при
следующем рефакторинге (что и произошло, когда TASK-022 скопировал паттерн TASK-019).

## ADR-0029: DOM-подмена (`dom-override`) — host/логика в shared-слое, переиспользование пикера, косметический инвариант

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-023 (PRD 7.5) требует «подмену DOM выделением» — косметическую замену
содержимого через element picker, **строго отдельно от сетевого мока** (разные ментальные
модели). Файл задачи буквально размещал фичу в `src/features/dom-override`, но её content-часть
(применение операций в ISOLATED-мире) инъектируется общим content-бандлом
(`content/inspection/index.ts`), которому fitness §12.1 запрещает импортировать `@/features/*`.

**Решение.** Host, чистый планировщик, типы и контракты — в
[`src/shared/inspection/dom-override`](../src/shared/inspection/dom-override) (как storage/forms/defects);
в фиче остаётся только поверхность (index/settings/ui/i18n/css). Выбор элемента переиспользует
существующий пикер (`inspection/pick`) — не отдельный оверлей. Переигрывание при мутациях DOM —
`MutationObserver` с защитой от циклов через **отключение наблюдателя на время собственных
записей** (наши мутации не попадают в его очередь). Инвариант — строго косметическая, ограниченная
выбором мутация: трогаем только текст/атрибут/инлайн-`display` выбранного узла; «вставка длинного
контента» пишет `textContent` (никогда `innerHTML` — без разметки/скриптов); каждая операция
снимает точный undo-снимок, поэтому `clear`/teardown полностью восстанавливают DOM. Контракты
`domOverride/apply|clear|list` (target `content`).

**Следствия.** Плюс: фича не нарушает инвариант расширяемости (бандл не зависит от фич), паттерн
единый со storage/forms/defects. Обязательно: content-хосты фич живут в shared и регистрируют
хендлеры в общей шине без собственного роутера. Минус: небольшое расхождение с буквой файла задачи
(размещение) — осознанное, задокументировано.

## ADR-0030: Экспорт «состояния бага» (`bug-report`) — приватный локальный артефакт, консоль как самодостаточный MAIN-буфер, переиспользование контрактов

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-025 (PRD 7.8) — собрать URL/окружение/storage/консоль/сеть активной вкладки в
воспроизводимый баг-репорт. Снимок может содержать секреты (токены в storage/cookies, тела запросов),
поэтому приватность — центральное требование; прямые интеграции с трекерами (внешняя сеть + креды) —
сознательно вне scope.

**Решение.** Артефакт формируется **локально** (Markdown + вложенный JSON), **без автоотправки**.
Секции **opt-in**; storage/cookies выключены по умолчанию (предупреждение о секретах), опциональное
маскирование редактит значения куки, «секретные» ключи storage и токены в URL. **Скачивание файла —
за явным подтверждением** (продуктовая безопасность); копирование в буфер — без ограничений. Сбор
консоли — **самодостаточный MAIN-кольцевой буфер** (ADR-0028: инлайн `STORE_KEY`/хелперы) с фоновой
ре-инъекцией при навигации, прикрытый `reserialize`-guard. Сетевая и storage-секции **переиспользуют
существующие контракты** (`mock/poll`, `storage/*`+`cookies/*`), не дублируя сбор; сеть типизируется
через **глобальный контракт сообщения** (`@/shared/messaging/contract`), а не импортом фичи мока
(fitness §12.1). Когда лог мока недоступен — секция честно помечается «недоступно». Чистые
композиция/рендер/маскирование — в coverage-gated `logic.ts`.

**Следствия.** Плюс: приватный по умолчанию инструмент без внешней сети; переиспользование, а не
дубль сбора; кросс-фичевая зависимость выражена через контракт сообщения, а не прямой импорт. Минус:
консоль ловится только с момента «arm» (буфер должен существовать до ошибок) — честно отражено в UI
(arm/disarm перед воспроизведением). Обязательно: любой новый MAIN-сборщик — с `reserialize`-тестом.

**Правка (2026-09-19).** Сетевая секция раньше молча зависела от того, что «Мок сети» заармлен на
вкладке ДО запросов — иначе `mock/poll` возвращал пустой лог и секция честно, но неожиданно давала
`available:false`. Добавлено **явное армирование записи сети** в самом bug-report (кнопка, симметрично
«arm console»): регистрирует потребителя «только лог» в разделяемой сессии перехвата через
`mock/observe` / `mock/observeStop` (см. ADR-0042). Ref-count снял конфликт с моком: наблюдение и
правила сосуществуют, армирование записи не затирает правила мока и не убивает его сессию. Чтение
по-прежнему `mock/poll` (без изменений).

## ADR-0031: Сценарии и троттлинг/офлайн мока — резолвер в UI-слое, троттлинг как action движка правил

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-023 достраивает ценностное ядро R2 поверх движка TASK-022: (1) группировать
правила в именованные **сценарии** с переключением одним тумблером; (2) **троттлинг/офлайн** на
запрос/домен. Нельзя раздувать инъектируемый MAIN-перехватчик и дублировать матчинг.

**Решение.** (1) Сценарий — именованная группа **ссылок на id правил** (единый источник правил —
`state.rules`; сценарий их не копирует). Чистый резолвер `resolveActiveRules(rules, scenarios,
activeId)` в [`scenarios.ts`](../src/features/mock-network/scenarios.ts) отдаёт плоский набор
действующих правил, который UI шлёт в перехватчик тем же `mock/apply` — **сценарии живут в
UI/настройках, перехватчик о них не знает** (контракт инъекции неизменен). Инвариант «ровно один
активный» держится структурно (одно поле `activeScenarioId`) и `normalizeActiveScenarioId` (висячий
id → null). (2) Троттлинг/офлайн — **поля action существующего движка правил** (`throttleKbps`,
`offline`), не новый перехватчик: чистый [`throttle.ts`](../src/features/mock-network/throttle.ts)
считает задержку `sizeBytes·8/kbps`, а самодостаточный MAIN-перехватчик применяет ту же формулу
инлайново (ADR-0028): офлайн → сетевая ошибка (`fetch` reject / XHR `error`), троттлинг → задержка
по размеру тела. Новые поля — через zod `.default()` (обратная совместимость: старое
сохранённое/импортируемое состояние не сбрасывается).

**Следствия.** Плюс: матчинг/мост не дублируются; перехватчик остаётся тонким; сценарии
экспортируются/импортируются (задел под шаринг TASK-029/030). Минус: `.default()` на полях action
делает вход схемы шире выхода → `defineMessage<Req>` схлопывает тип запроса к входной форме; в
background приводим распарсенные роутером данные к `MockRule[]` (комментарий на месте). Обязательно:
троттлинг/офлайн — только как action движка, не отдельный перехват.

## ADR-0032: Свободная линейка — интерактивный content-инструмент поверх собственного оверлея, чистый snap + переиспользуемая геометрия

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-033 — добор TASK-018: A↔B-измерение, box-model и чистая геометрия (`ruler/logic`)
уже были, но **свободный drag-измеритель + snap к кромкам** сознательно откладывались — им нужен
интерактивный слой поверх оверлея content-хоста (перетаскивание, live-рендер, teardown слушателей),
чего нет у страничных сборщиков `scan`/`collect`.

**Решение.** (1) **Геометрия не дублируется**: вектор A→B считает чистая `measureVector(a,b)` в той
же [`ruler/logic.ts`](../src/shared/inspection/ruler/logic.ts) (ΔX/ΔY/длина/угол/габариты, округление
до 0.5px как у `measureBetween`); snap — отдельный чистый модуль
[`ruler/snap.ts`](../src/shared/inspection/ruler/snap.ts) (`collectEdges`/`snapValue`/`snapPoint`:
притягивание по осям независимо, порог ≤0 отключает). Оба — без DOM, покрыты юнитами. (2)
**Интерактив — в content-бандле** ([`measure-tool.ts`](../src/content/inspection/measure-tool.ts)):
собственный закрытый Shadow-DOM оверлей (SVG-отрезок/bbox + подпись), слушатели в фазе перехвата на
`document`, кромки для snap собираются **один раз на старт drag** (бюджет узлов, перф §9), не на
каждый `mousemove`. Инвариант TASK-013 соблюдён — **DOM страницы не мутируется**. (3) **Контракт** —
долгоживущий `inspection/measure` (резолвится по завершении drag/отмене, как `pick`) + отдельный
`inspection/measureStop` (панель отменяет линейку; `inspection/teardown` принадлежит инспекционному
хосту). Хост линейки регистрирует хендлеры в общей шине, **свой роутер не поднимает** — его ставит
`installInspectionHost` (канон хостов storage/forms/dom-override). Single-flight: новый запуск/Stop/
`pagehide`/`Esc` полностью снимают слушатели и оверлей.

**Следствия.** Плюс: математика едина с TASK-018; инструмент самодостаточен и не связан с внутренним
оверлеем хоста; snap тестируется без браузера. Минус: свободная линейка — отдельное долгоживущее
сообщение (не переиспользует `pick`), т.к. семантика иная (drag, а не клик). Обязательно: любой
интерактив над страницей — поверх собственного Shadow-оверлея с teardown по канону single-flight, без
мутации DOM.

## ADR-0034: Канонический `uuidV4` в `shared/test-data` на инъектируемом `RandomSource`; фичи делегируют

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-034 вводит foundation-слой генераторов тест-данных
([`shared/test-data`](../src/shared/test-data)) и требует не дублировать UUID v4 (был в
`features/timestamp-hash`). Но `shared/**` не может импортировать `@/features/*` (fitness §12.1) —
импорт «из фичи в shared» запрещён.

**Решение.** UUID v4 реализован **один раз канонически** в
[`smart.ts`](../src/shared/test-data/smart.ts) на инъектируемом `RandomSource` (RFC-4122: version-нибл
`4`, variant-биты `10`), рядом с прочими «умными» значениями — карта по Луну, IBAN по mod-97. Все
выборки — через `RandomSource.below(n)` (rejection sampling, без modulo-bias, инвариант TASK-006),
локали/форматы — данные-таблицы. `features/timestamp-hash` **делегирует** этому shared-UUID
(feature→shared — разрешённое направление), сохранив нативный fast-path `crypto.randomUUID`. Формы
(`shared/inspection/forms/logic.ts`) переведены на `shared/test-data`, дублирующие таблицы удалены.
Валидность проверяема: тесты подтверждают Луна/mod-97/RFC-4122 и детерминизм при фиксированном источнике.

**Следствия.** Плюс: единый алгоритм UUID без дрейфа; DRY в правильном направлении (фича→shared);
переиспользуемый слой под будущие пресеты. Минус: нативный `crypto.randomUUID` остаётся отдельной
быстрой веткой (не через `RandomSource`) — сознательно, ради производительности и энтропии платформы.
Обязательно: любые доменные генераторы тест-данных — в `shared/test-data`, рандом только через
`RandomSource`, выборки через `below`.

## ADR-0035: Скриншот с аннотациями — захват через platform-seam, склейка полной страницы content-хостом, деструктивная замазка

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-027 (PRD §7.8): QA нужен локальный визуальный артефакт — снимок видимой области / элемента / полной страницы с лёгкой разметкой (рамка/стрелка/линия/текст/замазка), без внешней сети. Захват кадра (`chrome.tabs.captureVisibleTab`) живёт на стороне расширения; полная страница требует управляемой прокрутки страницы; замазка — это про приватность (не должна сниматься).

**Решение.** Захват кадра — через новый platform-seam `capture.visibleTab` (единственная точка доступа к `chrome.tabs.captureVisibleTab`, ADR-0014). Вся детерминированная геометрия (кроп по DPR, план склейки `planFullPageStitch`, клэмп координат, модель аннотаций + порядок рендера) — в чистом `features/screenshot/logic.ts` (~100% покрытие). Склейка полной страницы — цикл «RPC-прокрутка → снять кадр seam'ом → нарисовать срез» поверх нового content-хоста `shared/inspection/screenshot/scroll-host.ts` (`screenshot/metrics|scrollStep|reset`, свои сообщения регистрируются дескриптором фичи, роутер поднимает инспекционный хост). Замазка применяется **деструктивно к пикселям** экспортируемого PNG (не CSS/canvas-оверлей). Экспорт — копирование в буфер + скачивание **после подтверждения**; никакой внешней сети.

**Следствия.** (+) Пиксели замазки не восстановимы из файла (приватность). (+) Геометрия тестируема без браузера; хост — тонкий, в общем инспекционном бандле (не тянет фичи, fitness §12.1). (−) Полная страница best-effort: sticky/fixed и ленивый контент при склейке могут задваиваться — честно помечено в UI, не обещаем пиксель-перфект. Обязательно: захват — только через seam; скачивание — только с подтверждением.

**Правка (2026-09-05).** Первая реализация запрашивала под захват host `*://*/*` — как остальной инспекционный слой. Это баг: Chrome-гейт `chrome.tabs.captureVisibleTab` (`CanCaptureVisiblePage`) принимает **только** литеральный токен `<all_urls>` либо `activeTab`; `*://*/*`, даже будучи выданным брокером, гейт отвергает — рантайм падал «Either the '<all_urls>' or 'activeTab' permission is required». Исправлено: скриншот запрашивает host `<all_urls>` (добавлен в `optional_host_permissions`, не заменяя `*://*/*` для прочих фич). Взят `<all_urls>`, а не `activeTab`: последний покрывает лишь вкладку в момент инвокации и не переживает переключение вкладок в side panel (ADR-0022); тот же грант покрывает host-доступ инъекции пикера/склейки. Остаётся opt-in под жестом (ADR-0013).

## ADR-0036: IndexedDB/Cache в редакторе состояния — продолжение storage-editor, безопасная сериализация, генерический форвардинг

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-031 расширяет состояние вкладки сверх storage/cookies (TASK-017) на IndexedDB и Cache Storage — клиентские хранилища, которые QA сейчас смотрит в DevTools. Значения IDB бинарны/структурны (`structuredClone`-типы), Cache-ответы бывают `opaque`/большими/бинарными.

**Следствия.** (+) Один редактор состояния на все клиентские хранилища; переиспользованы паттерны снимка/диффа/быстрой очистки/подтверждений. (−) `host.ts` низко покрыт юнитами (реальные async-API) — сознательно, компенсируется e2e. Обязательно: деструктив — только с подтверждением; экспорт снимка предупреждает о секретах.

## ADR-0037: Синк настроек — только `chrome.storage.sync`, LWW-слияние, порты вместо связей с фичами

**Статус:** Accepted · **Дата:** 2026-09-05

**Контекст.** TASK-029 (PRD §7.8/§11, open-core): перенос выбранных пространств настроек/пресетов между устройствами одного пользователя без нашего бэкенда. Не командный шаринг (это TASK-030, Pro, — не в работе). Квоты `sync` малы (~100KB total / ~8KB item / ~512 items).

**Решение.** Синк только поверх `chrome.storage.sync` (аккаунт браузера), новый platform-seam `storageSync`, экспортируемый как `StorageSyncSeam | undefined` — при отсутствии API движок грациозно деградирует (`isAvailable() === false`), а не падает. Чистая логика (`logic.ts`, ~100%): LWW-слияние по `updatedAt`, детект конфликта (обе стороны менялись с базы → маркер), оценка размера против квот (per-item + total + items), версионирование конверта + миграции. Фича НЕ импортирует другие фичи и НЕ правит `shared/storage` (fitness §12.1): работает через порт `NamespaceStore` (инжектируемые read/write сырого блоба namespace'а); конкретные биндеры собирает `instance.ts` из публичного API (`appSettings`). Каталог синкаемых пространств не содержит секретов (снимки storage/cookies, логи — никогда). Синк — opt-in с подтверждением приватности; выключение — с очисткой `sync`.

**Следствия.** (+) Приватность и open-core-обещание (нет бэкенда). (+) Логика слияния/квот полностью тестируема векторно; порт держит фичу дизъюнктной. (−) Пока связано одно пространство `app`; биндеры пресетов генераторов — добор (их id в каталоге, но без биндера строки в UI не показываются). Обязательно: только `chrome.storage.sync`; секреты не синкать; локальный слой — источник истины.

## ADR-0038: Мок сети — CDP как второй транспорт (`chrome.debugger`/`Fetch`), гарантированный жизненный цикл, install-time право

**Статус:** Accepted · **Дата:** 2026-09-06

**Контекст.** TASK-032 (PRD §9, стратегия перехвата): MAIN-путь (обёртки `fetch`/XHR, TASK-022) не ловит запросы в обход обёрток — из воркеров, `sendBeacon`, ресурсы страницы — и бессилен при строгом CSP. PRD закладывал «опциональный CDP-режим для сложных кейсов». UI уже нёс сегмент MAIN/CDP, но CDP был заглушкой (`cdp-not-implemented`).

**Решение.** CDP — **второй транспорт того же движка**: правила/сценарии/троттлинг не меняются, вся корректность резолва остаётся в чистой `mock-network/logic.ts` (+`throttle.ts`), а CDP-слой лишь транслирует уже принятое решение в команды `Fetch.*`. Новый platform-seam `debuggerSeam` (`attach`/`detach`/`sendCommand`/`onEvent`/`onDetach`, единственная точка доступа к `chrome.debugger`, ADR-0014). `Fetch.enable` перехватывает всё на Request-стадии; матчинг остаётся в JS (`logic.matchRule`, glob→regex, компиляция один раз, ReDoS-safe) — CDP-паттерны это просто `[{urlPattern:'*'}]`. Резолв → `fulfillRequest` (literal/json), `failRequest` (offline/сетевая ошибка), либо passthrough-оверлей статусов/заголовков двухстадийно (`continueRequest{interceptResponse}` → Response-стадия `getResponseBody`+`fulfillRequest`, корреляция по CDP `requestId`, fail-open на любой ошибке). Троттлинг — задержкой перед командой. Жизненный цикл (`lifecycle.ts`): идемпотентный attach (повторный лишь обновляет правила), **detach гарантирован во всех ветках** (выключение / `tabs.onRemoved` / ошибка attach|enable / пользовательский `onDetach` — последний очищает состояние БЕЗ повторного detach, браузер уже освободил сессию). Право `debugger` — **install-time** (см. ниже); MAIN остаётся дефолтом, отказ/конфликт CDP → грациозный fallback на MAIN.

**Следствия.** (+) Ловит трафик в обход MAIN-обёрток и при строгом CSP, паритет резолва с MAIN без дублирования логики (25 юнитов на транспорт+lifecycle). (+) Гарантированный detach исключает «повисшую» debug-сессию (вечный баннер + заблокированный DevTools). (−) **Chrome ЗАПРЕЩАЕТ `debugger` в `optional_permissions`** (тот же список, что и `declarativeNetRequest`) — поэтому право install-time, и в отличие от host-гейтного DNR оно **поднимает install-warning** («доступ к отладчику страниц») для всех, включая тех, кто CDP не трогает. Сознательный компромисс (решение пользователя): ценность второго транспорта перевешивает; opt-in сохраняется на уровне действия — attach и его баннер возникают только под жестом при выборе CDP. (−) CDP Requests-лог фиксирует только перехваченные (сматченные) запросы; исчерпывающий лог трафика остаётся за MAIN. (−) Конфликт с внешним DevTools/отладчиком на той же вкладке честно предупреждается, не решается. Обязательно: `chrome.debugger` — только через seam; detach во всех ветках; резолв не дублировать.

**Альтернативы.** `debugger` за build-флагом (чистый install по умолчанию, CDP только в advanced-сборке) — отклонено пользователем в пользу единой сборки; простота дистрибуции важнее, install-warning принят.

## ADR-0039: In-page («заморозка экрана») редактор скриншота как content-оверлей

**Статус:** Accepted · **Дата:** 2026-09-06

**Контекст.** TASK-035 (добор TASK-027): редактор в side panel отрывает снимок от страницы — лишний контекст-свитч. QA привыкли к Lightshot: нажал → экран «замёрз» → тянешь рамку прямо по странице → инлайн-тулбар → рисуешь на месте. Нужен in-place поток, переиспользующий готовую чистую логику TASK-027, с side panel как фолбэком.

**Решение.** On-page оверлей поверх собственного **закрытого Shadow-DOM** (образец — `measure-tool.ts`, DOM страницы не мутируется, инвариант TASK-013): `captureVisibleTab` недоступен в контент-скрипте, поэтому кадр снимает расширение (существующий seam `capture.visibleTab`) и передаёт его оверлею новым `target:'content'` RPC `screenshot/editInPage` (dataURL + размеры + локализованные подписи); оверлей «замораживает» кадр на fixed-canvas, даёт drag-выделение с затемнением, инлайн-тулбар и те же инструменты. **Реюз, не переписывание**: switch по `kind`, деструктивная замазка и история undo/redo вынесены в общий чистый модуль `shared/inspection/screenshot/draw.ts` — один источник для обеих поверхностей (инспекционный content-бандл НЕ может импортировать фичу, fitness §12.1), `features/screenshot/logic.ts` ре-экспортирует его для обратной совместимости. Чистая геометрия выделения/тулбара/DPR — новый `region.ts` (28 юнитов). Экспорт — в контент-мире: копирование (`ClipboardItem`) и скачивание **после подтверждения**, кроп по выделению с учётом DPR.

**Следствия.** (+) In-place поток без контекст-свитча; вся ценность TASK-027 переиспользована (нулевое дублирование рендера). (+) Оверлей изолирован (закрытый Shadow-DOM, чистый teardown, без мутаций DOM страницы); новых прав нет (`<all_urls>`+`scripting` уже есть, opt-in под жестом), внешней сети нет. (−) Честные границы песочницы: только вьюпорт активной вкладки (не рабочий стол/хром браузера); полная страница и неинъектируемые схемы (`chrome://`, магазин, `view-source:`, страницы расширений/`file://`/PDF) → фолбэк на side panel с понятным сообщением. (−) Тулбар в **закрытом** Shadow-DOM недоступен e2e-клику: корректность PNG/замазки покрыта юнитами `draw`/`region`, e2e проверяет запуск+заморозку+выделение+чистый teardown по Esc. Обязательно: инвариант TASK-013 (без мутаций DOM); рендер не дублировать (общий `draw.ts`).

**Правка (2026-09-22, см. ADR-0046).** Ревизовано по отчёту пользователя: (1) снят пункт «скачивание только с подтверждением» — PNG скачивается **немедленно**, как в side panel (баннер подтверждения удалён из обеих поверхностей); (2) поле подписи переведено на плавающий `position: fixed` инпут в точке клика (Paint-стиль) вместо встроенного в тулбар инпута с кнопкой; (3) добавлен **модальный экран событий** на границе `host` (`SHIELDED_EVENTS`, `stopPropagation` в фазе всплытия) — закрывает утечку кликов/клавиш из composed-событий Shadow-DOM в делегированные `document`/`window`-слушатели «замороженной» страницы.

## ADR-0040: Мок сети — Replay-петля с sender в background (обход CORS), граница «не Postman»
**Статус:** Accepted · **Дата:** 2026-09-06

**Контекст.** TASK-038 (добор TASK-022/023/032): мок-ядро ловит и подменяет ответ, но не умеет «поймал → поправил → отправил заново → посмотрел ответ» — а это ~80% причин, по которым QA открывает Postman. Нужна replay-петля в контексте страницы, но сознательно НЕ полноценный API-клиент (PRD §3).

**Решение.** Отправка replay-запроса — в **service worker через `mock/replay` RPC**, а не из MAIN-world: так есть host-право и обход CORS страницы (для QA-инструмента это фича, не баг), и нет зависимости от CSP страницы. Sender (`replay/sender.ts`) принимает **инъектируемый `fetch`** (тестируемость без платформы; `fetch` — веб-глобал SW, не `chrome.*`, поэтому platform-seam и не нужен, ADR-0014 не нарушен): `AbortController` + таймаут + кап размера ответа; возвращает **типизированный дискриминированный Result** (`network`/`timeout`/`too-large`/`aborted`/`bad-request`), ошибки едут данными, а не throw в UI. Чистая логика (`logic.ts`): `RequestSpec`/`ResponseMeta`, сборка/разбор URL+query, префилл из `CaughtRequest` (метод/URL/query; заголовки/тело пусты — снимок их не несёт), сериализация в cURL (POSIX-экранирование). pretty/minify JSON — **локальные** best-effort хелперы в `logic.ts`, а НЕ импорт из фичи `decoders` (инвариант расширяемости §1: фичи не импортируют друг друга — это ловил бы fitness-тест). История — лёгкая, в namespace `mock-network` через обратносовместимый zod `.default([])`.

**Следствия.** (+) Замыкает перехват в петлю без выхода в Postman; обход CORS ожидаемо полезен. (+) Ошибки типизированы, UI не падает; host-право под жестом, манифест не менялся (host уже optional). (−) **Побочные эффекты реальны**: переотправка не-`GET`/`HEAD` меняет данные на настоящем сервере → перед отправкой обязателен явный confirm, никакого автоповтора; «Повторить» из истории загружает спек в редактор (снова через confirm), а не бьёт сразу. (−) Осознанное мелкое дублирование JSON-форматтера ради чистой границы фич. Запрещено (граница «не Postman», PRD §3): коллекции/окружения/переменные-профили, OAuth/подписи, pre/post-скрипты, ассерты, раннеры, импорт OpenAPI.

## ADR-0041: Bug-report — событийный timeline действий (MAIN-world кольцевой буфер, маскирование, opt-in)
**Статус:** Accepted · **Дата:** 2026-09-06

**Контекст.** TASK-036 (добор TASK-025): конкуренты (Jam, Marker.io) авто-собирают «шаги воспроизведения» и переплетают их с консолью/сетью на одной шкале — это резко ускоряет воспроизведение. TASK-025 собирал снимок без временно́й шкалы. Приватность — центральное требование (ADR TASK-025): никакой автоотправки.

**Решение.** Новый сборщик `collectors/actions.ts` — **самодостаточная MAIN-world функция** (инъекция через `func.toString()`, ADR-0028): кольцевой буфер фикс-размера (`≈200`, без утечки на долгих сессиях), делегированные пассивные слушатели на `document` с единым teardown, **никаких `preventDefault`**; устойчивый селектор цели строится **инлайн** внутри тела (импортировать общий хелпер в инъектируемую функцию нельзя). Ловим click/input/change/submit/навигацию (`pushState`/`hashchange`/`popstate`)/жесты-keydown (Enter/Esc/Tab/стрелки, НЕ посимвольно)/debounced resize. Чистая логика (`logic.ts`): дискриминированный `TimelineEvent` (`action`/`console`/`network`), слияние потоков и стабильная сортировка по монотонному таймстемпу (`performance.now()`-базис + wall-clock якорь, отдаваемый `readActionsBuffer`), относительные таймкоды, детерминированный Markdown-рендер, маскирование. Секция «Шаги воспроизведения (авто)» в Markdown + `timeline[]` в JSON-артефакте; схемы артефакта и настроек расширены **обратносовместимо** (старые снимки без `timeline` валидны, секция по умолчанию **выключена**). Re-serialization-тест доказывает самодостаточность инъектируемых функций.

**Следствия.** (+) Авто-«steps to reproduce» на единой шкале с консолью/сетью — заметный шаг к паритету с Jam/Marker.io без session-replay. (+) Переиспользован каркас TASK-025 (сборщик консоли, схема, маскирование, UI). (−) **Приватность прежде полноты**: значения ввода маскируются по умолчанию, `type=password` не читается ни при каких настройках, timeline прикладывается только по явной галочке, автоотправки/внешней сети нет. (−) Только top-документ активной вкладки (iframes честно помечаются пропуском); не пиксельная перезапись (rrweb — вне scope, это TASK-037). Обязательно: инъектируемые сборщики самодостаточны (ADR-0028); маскирование — дефолт; timeline — opt-in.

**Правка (2026-09-19).** Обнаружены и исправлены три дефекта записи. (1) **Stop терял шаги.** `stopRecording` вызывал полный `clearActionsBuffer` (`window[STORE_KEY] = undefined`), поэтому естественный сценарий «Start → воспроизвёл → **Stop** → Capture» отдавал пустой таймлайн. Разделили жесты: `clearActionsBuffer(keepLog)` — `keepLog:true` (Stop) снимает хуки со страницы, но **оставляет лог читаемым и замороженным** (`paused=true`) для последующего Capture; `keepLog:false` (Reset / новый Start) — полный сброс. Новый Start сначала сбрасывает остаток, затем ставит свежий буфер (идемпотентный install не переустановил бы слушатели поверх отцепленного стора). (2) **Хрупкая публикация стора.** Стор публиковался на `window` ПОСЛЕ навешивания слушателей и патча `history.*`; на странице, где `history.pushState`/`replaceState` защищены, частичный сбой оставлял буфер нечитаемым. Теперь стор публикуется **первым** (как у mock-перехватчика), а патч history изолирован в `try/catch` (теряется лишь детект SPA-навигации). (3) Явно оформлено: значимый сценарий воспроизведения часто включает навигацию, а MAIN-буфер её не переживает — известная граница (см. ADR-0028), не бага записи.

## ADR-0042: Разделяемая ref-count сессия перехвата сети (владелец MAIN-перехватчика, потребители по токену)

**Статус:** Accepted · **Дата:** 2026-09-19

**Контекст.** Сетевой лог (наблюдение за всеми fetch/XHR) и мокинг (правила подмены) живут в ОДНОМ MAIN-перехватчике на вкладку (ADR-0027). «Мок сети» (TASK-022) владел им напрямую: реестр `active: Map<tabId, rules>` в фоне + собственный reinject-слушатель. Когда «Экспорт бага» (TASK-025/036) добавил запись сети, он переиспользовал перехватчик через `mock/apply` с пустыми правилами — и вскрылся конфликт совладения: (1) армирование лога `apply([])` **затирало** правила активного мока; (2) выключение записи (`mock/clear`) **убивало** сессию мока; (3) у каждой фичи было своё UI-состояние без синхронизации — рассинхрон. Дублирования кода не было (реюз через глобальный контракт, fitness §12.1), но владение было сломано.

**Решение.** Владельцем жизненного цикла MAIN-перехватчика делаем **разделяемую сессию с подсчётом потребителей** — `shared/inspection/network/capture-session.ts`, `createNetworkCaptureSession<Rule, Entry>`. Generic и без `chrome.*` (ADR-0014): платформенные `install`/`clear`/`read` и события вкладок инъектируются как зависимости (juнит-тестируется без Chrome). Инварианты: перехватчик **жив, пока есть хотя бы один потребитель** (токен: `'mock'` — со своими правилами, `'observer'` — «только лог», пустые правила); действующие правила — **объединение вкладов** всех потребителей (логирование включено всегда, мокинг — оверлей); ре-инъекция при навигации и teardown — **внутри сессии**, один раз. Единственный инстанс создаёт **владелец движка** (фон мока, с реальным `installMockInterceptor`/`clearMockInterceptor`/`readMockLog`); прочие фичи ходят к нему через глобальные контракты `mock/observe` / `mock/observeStop` (fitness §12.1: без импорта фичи). `mock/apply`→`acquire('mock')`, `mock/clear`→`release('mock')`, `mock/poll`→`read`. CDP-транспорт (ADR-0038) остаётся отдельным mock-only путём со своей гарантией освобождения отладчика; сессия управляет MAIN — общий и частый случай, где и были конфликты.

**Следствия.** (+) Три конфликта сняты: наблюдатель и мок **сосуществуют** — армирование записи не затирает правила, выключение не убивает чужую сессию, перехватчик снимается только при нуле потребителей. (+) Наблюдение за сетью стало **переиспользуемой инфраструктурой** (shared), а не приватной деталью мока; появление третьего потребителя не плодит дубль и не рискует клоббером. (+) Ref-count/merge/reinject покрыты юнит-тестами на фейках. (−) Смешение MAIN-наблюдения и CDP-мока на одной вкладке — редкий край вне scope: `poll` отдаёт связный лог (CDP-лог при CDP-сессии, иначе MAIN), но общий ref-count на CDP пока не распространён (отдельная задача, риск по отладчику). Обязательно: MAIN-перехватчик трогают только через сессию/контракты, а не напрямую из фич.

## ADR-0043: Транспорты доставки баг-репорта агенту без установки — deep link + File System Access + буфер

**Статус:** Accepted · **Дата:** 2026-09-19

**Контекст.** TASK-040 (добор TASK-025/036): «Экспорт состояния бага» строит `BugArtifact` (Markdown + машиночитаемый JSON), но доставка — только «Скопировать»/«Скачать». Запрос: **по одной кнопке отправить баг-репорт в AI-харнес** (Claude Code, Codex, Cursor), чтобы агент дальше работал с ним, **без установки какого-либо стороннего софта** (жёсткое требование). MV3-расширение изолировано от ФС и процессов; локальный companion/native-messaging нарушил бы «без установки». Ключевое открытие: у агентов есть **deep links** (custom URL schemes), которые регистрирует само приложение-агент (у Claude Code — при первом интерактивном промпте, без отдельной установки) и которые открывают агента с уже впечатанным промптом. Ограничение: `q` у Claude Code — **5 000 символов**, полный отчёт туда не влезает; из браузера **нельзя определить**, зарегистрирована ли схема.

**Решение.** Ядро (`bug-report/handoff/*`) + **три локальных транспорта без установки**, ранжированных по близости к one-click: **deep link** (запускает агента с впечатанным промптом) → **File System Access** (полный артефакт в корень репозитория; нужен, т.к. `q` ≤ 5k) → **буфер** (универсальный фолбэк). Суть дизайна — **связка «файл + deep link»**: FSA пишет полный `.md`/`.json`/`latest.md` в `.qaid/bug-reports/` выбранной папки-корня, а deep link несёт **короткий** промпт-указатель на `latest.md` + суть (заголовок, URL, топ-ошибка). Границы модулей disjoint (параллелились субагентами): `packager.ts` (чистая сборка пакета + компактного промпта, гарантированно ≤ лимита с честной пометкой усечения), `deep-link.ts` (чистый строитель URL: URL-encode, `%0A`, **жёсткая гарантия `q` ≤ лимита** через усечение с указателем на файл, валидация `cwd` — запрет `..`/UNC/control/bidi, зеркалит правила Claude Code — и `repo=owner/name`), `targets.ts` (реестр `HandoffTarget` по образцу `features/registry.ts` + базовые тул-независимые адресаты `clipboard`/`project-folder`; тул-специфичные — TASK-043/044/045), `transports/{fs-access,clipboard}.ts`. Транспорты **инъектируются** в `deliver(ctx)` как зависимости → адресат тестируется на фейках без DOM/chrome. FSA работает только из document-контекста (popup/side panel), handle персистится в IndexedDB с перезапросом `readwrite`-доступа. Таргет проекта (`repo`/`cwd`) задаёт пользователь **один раз** в настройках, т.к. FSA-handle не раскрывает абсолютный путь (безопасность браузера) — это конфиг, не установка.

**Следствия.** (+) One-click-путь до агента (deep link) с обходом лимита 5k через файл, всё локально. (+) Расширяемо: новый агент = новый `HandoffTarget` поверх общего `buildDeepLink`/FSA/буфера, без правки ядра (адаптеры TASK-043/044/045 параллелятся — свой файл + свои строки, disjoint write-set). (+) **Никаких новых прав** (см. [PERMISSIONS.md](PERMISSIONS.md)): File System Access — веб-API со своим жестом-пикером; deep link — `window.open` под жестом; буфер — document-контекст. (−) **Нельзя детектировать регистрацию схемы** из браузера → открываем deep link оптимистично и **всегда** показываем фолбэк (файл/буфер); «не открылось» — не ошибка, а ветка на альтернативу, никогда не тихий провал. (−) Промпт by design **не отправляется сам** (Enter жмёт пользователь) — тост это явно проговаривает. (−) Приватность (PRD §6/§9): доставляются только выбранные секции с маскированием (цепочка TASK-025), **ничего в сеть**, запись/открытие — под явным согласием. Обязательно: deep link открывать только под жестом из документа (не `chrome.tabs.create` с кастомной схемой); MAIN/FSA — не из service worker; промпт строить ПОВЕРХ `renderMarkdown`/`renderJson`/`renderTimeline`, не заново. Запрещено: любой локальный процесс/бинарь, авто-отправка во внешнюю сеть.

**Правка (2026-09-20) — три равноправных входа Claude Code, а не один.** У Claude Code оказалось **три** способа принять deep link, и все три реализованы как ОТДЕЛЬНЫЕ адресаты в селекте (честнее скрытого тумблера — пользователь видит все пути и выбирает осознанно), поверх одного `makeDeliver`/деградации в `targets/claude-code.ts`: (1) **терминал** `claude-cli://open` (order 1, дефолт, лимит `q` 5k); (2) **десктоп-приложение Claude** `claude://code/new?q=…&folder=<abs>` (order 2) — открывает вкладку Code в GUI, **аналог Codex `codex://new`**; (3) **VS Code** `vscode://anthropic.claude-code/open` (order 3). Схема/путь каждого — в одной константе `LINK`, `buildClaudeDeepLink` принимает `variant: 'terminal'|'vscode'|'desktop'`. **Зачем десктоп-вариант:** терминальный `claude-cli://` на Windows запускается через лаунчер `wt.exe -d <cwd>` и имеет две среды-зависимые причины «окно мелькнуло и закрылось» — нет Windows Terminal (не предустановлен на Win10) и несуществующий `cwd` (см. память `handoff-fsa-constraints` п.4). Путь `claude://` открывает GUI-приложение напрямую → **обходит обе**: не нужен Windows Terminal, нет флэш-клоуза. Семантическое отличие: схема `claude://code/new` **не понимает `repo`** — рабочая папка идёт только из валидного абсолютного `cwd` в параметр `folder` (через `buildDeepLink` `extraParams`); непустой-невалидный `cwd` → `invalid-cwd` → та же деградация (открыть без папки, `openedNoTarget`); пусто/только `repo` → дефолтная папка. Требует установленного десктоп-приложения (оно регистрирует `claude://`) — детект схемы из браузера по-прежнему невозможен, поэтому те же всегда-видимые фолбэки. Открытый вопрос (продуктовое решение, не сделано): делать ли десктоп-вариант ВЫБРАННЫМ по умолчанию на Windows.

## ADR-0044: Авто-обнаружение баг-репортов агентом без установки — rule-файлы + опциональный off-the-shelf npx-MCP

**Статус:** Accepted · **Дата:** 2026-09-19

**Контекст.** TASK-042 (добор R4 поверх TASK-040/043/044/045): deep link впечатывает короткий промпт-указатель на `.qaid/bug-reports/latest.md`, но чтобы агент понимал этот путь «из коробки» и чтобы стало возможным «разбери последний баг» вообще без пути — нужно, чтобы агент **сам находил** свежий репорт. Требование волны неизменно: **без установки** какого-либо софта.

**Решение.** Два опциональных, не требующих установки механизма, генерируемых чистым модулем `handoff/discovery.ts` (без DOM/`chrome.*`) и записываемых через тот же FSA-транспорт (TASK-040): (1) **rule-файлы** — это обычные текстовые файлы репозитория, не софт: секция-инструкция «репорты в `.qaid/bug-reports/`, свежий — `latest.md`» в `CLAUDE.md` / `.cursor/rules/qaid.md` / `AGENTS.md`, вставляемая **идемпотентно по маркеру** (`<!-- qaid:begin/end -->` — повторная запись обновляет секцию, не плодит дубли и не затирает пользовательский файл); (2) **опциональный npx-MCP** — фрагмент конфига для off-the-shelf `@modelcontextprotocol/server-filesystem` через `npx -y`, направленный на папку репортов, для `.mcp.json`/`.cursor/mcp.json` (JSON, мердж сохраняет прочие серверы пользователя) и Codex `~/.codex/config.toml` (TOML, фрагмент для вставки). Node уже есть у пользователей Claude Code/Codex; `npx` ничего не «ставит» в привычном смысле, а **свой** MCP-сервер мы не публикуем и не бандлим. Абсолютный путь папки репортов FSA не раскрывает → берётся из таргета проекта (разовый ввод пользователя, как в TASK-040) либо показывается плейсхолдером `<путь>` с честной пометкой ограничения. UI даёт предпросмотр + «Записать в проект» (FSA) / «Скопировать».

**Следствия.** (+) «Разбери последний баг» становится самодостаточным (rule-файлы), а для желающих — агент видит репорты как MCP-ресурсы (npx-MCP) — всё без установки и без нашего сервера. (+) Идемпотентный мердж не разрушает пользовательские `CLAUDE.md`/`config.toml`. (+) Генераторы чистые, покрыты ~100% (валидность JSON — `JSON.parse`; TOML-фрагмент — структурные ассерты, TOML-парсера в зависимостях нет и не добавляем). (−) **Опция, а не требование**: ценность даёт уже TASK-040/043 (deep link + файл), поэтому фича — под-действие, не на главном пути; npx-MCP помечен «нужен Node/npx». (−) Абсолютный путь — разовый ручной ввод (граница безопасности браузера), иначе плейсхолдер. Приватность: rule-файлы и конфиги содержат только пути/инструкции, **никаких данных репорта**. Запрещено: публиковать/бандлить собственный MCP-сервер или бинарь.

## ADR-0045: Запись экрана — offscreen-`MediaRecorder`, захват через `streamId`, доставка `Blob` по `BroadcastChannel`

**Статус:** Accepted · **Дата:** 2026-09-20

**Контекст.** TASK-037 добавляет локальную запись экрана/вкладки с аудио (WebM, без облака) — самый заметный пробел против Jam/Marker.io. MV3-капкан известен: `MediaRecorder` недоступен в service worker. Исходная постановка предлагала вести захват в offscreen-документе «или side panel», источник — `chrome.tabCapture` и/или `navigator.mediaDevices.getDisplayMedia`. При реализации всплыли три факта, ломающие наивную схему: (1) **`getDisplayMedia` нельзя вызвать из offscreen** — он требует transient user activation, которой в offscreen нет; (2) **`MediaStream` не сериализуем** — поток, полученный жестом в side panel, нельзя прокинуть в offscreen через сообщение; (3) **итоговый `Blob`/`objectURL` привязан к контексту-создателю** — вернуть видео из offscreen в UI через `chrome.runtime` можно только base64-раздуванием.

**Решение.** Запись ведёт **единственный offscreen-документ** (`chrome.offscreen`, reasons `USER_MEDIA`/`DISPLAY_MEDIA`), а не side panel: side panel закрывается/переживает смену вкладки ненадёжно, offscreen живёт независимо от эфемерного SW. Источник видео — **`streamId`, а не поток**: привилегированный SW добывает идентификатор (вкладка → `chrome.tabCapture.getMediaStreamId`; экран/окно → системный пикер `chrome.desktopCapture.chooseDesktopMedia`, что и есть согласие, аналог `getDisplayMedia`), offscreen конструирует поток локально через `getUserMedia({ video:{ mandatory:{ chromeMediaSource:'tab'|'desktop', chromeMediaSourceId: streamId } } })`. Микрофон — `getUserMedia({audio:true})` в offscreen (рантайм-промпт); mic+звук вкладки микшируются `AudioContext`/`MediaStreamAudioDestinationNode`; при записи звука вкладки поток заворачивается обратно на `destination`, чтобы пользователь продолжал слышать вкладку.

**Две плоскости обмена.** Классическая MV3-гонка «несколько listener'ов на `chrome.runtime.onMessage`» (SW-роутер vs offscreen) обойдена разделением каналов: **команды рекордеру и доставка `Blob`** идут по **`BroadcastChannel('qa-screen-recording')`** между side panel и offscreen (same-origin, structured clone переносит `Blob` без base64; UI роутер сообщений не ставит → интерференции нет). По **типизированной шине** (`shared/messaging`) идут только привилегированные операции, доступные исключительно из SW: `screenrec/start` (добыть `streamId` + поднять offscreen + бейдж-индикатор `chrome.action`) и `screenrec/finalize` (снять бейдж + закрыть offscreen). Чистое ядро `logic.ts` (выбор MIME за seam `isTypeSupported`, лимиты длительности/размера, таймер, машина состояний-редьюсер, имя файла) — без DOM/`chrome.*`, покрытие 100%.

**Права.** `offscreen` + `tabCapture` + `desktopCapture` — **install-time, а НЕ optional**: Chrome отвергает `tabCapture`/`desktopCapture` в `optional_permissions` (тот же класс, что DNR/`debugger`, ADR-0026/0038). Тот же принятый компромисс: API-грант install-time, но **наблюдаемый эффект — только под жестом + системным пикером/промптом микрофона**. `offscreen` install-warning не поднимает; у `tabCapture`/`desktopCapture` он минимален. Микрофон — без манифест-права (браузерный промпт).

**Следствия.** (+) Реализуемый, прод-путь захвата вкладки/экрана/окна с аудио, целиком локально; после стопа все треки останавливаются (`track.stop()`) и offscreen закрывается — «висящего» захвата нет. (+) Границы модулей disjoint (параллелились субагентами): чистое ядро+тесты, движок (`background.ts` streamId+offscreen+бейдж / `capture.ts` микшер / `recorder.ts` обёртка / `src/offscreen/index.ts`), UI+i18n+тест — без конфликтов и оверрайдов. (+) `BroadcastChannel` устраняет и гонку мультилистенеров, и base64-раздувание видео. (−) **Отклонены** `getDisplayMedia` и запись в side panel (нереализуемо/ненадёжно — см. Контекст). (−) Системный звук при `desktopCapture` в MVP не пишется (платформенно ограничен) — только звук вкладки (`tabCapture`) и микрофон; расширение — отдельный добор. (−) Если side panel закрыт в момент авто-стопа по лимиту, готовый `Blob` некому принять — панель остаётся управляющей поверхностью на время сессии (честно задокументировано). (−) Полный сквозной захват **не воспроизводим в headless** (нативный пикер/промпт): e2e проверяет отрисовку + примитив `MediaRecorder`→WebM, привилегированный захват — ручная проверка на load-unpacked. **Запрещено:** запись без жеста пользователя; любая авто-отправка видео во внешнюю сеть; обход системного пикера/промпта; доступ к `chrome.*` вне `src/platform`.

**Ревизия 2026-09-20 — бесшовный tabCapture в UI + запасной пикер, когда нет гранта `activeTab`.** На реальном Chrome старт падал: `Extension has not been invoked for the current page (see activeTab permission)` и `A target tab is required when called from a service worker context`. Причина: `chrome.tabCapture.getMediaStreamId` требует **transient user activation И персистентного гранта `activeTab` целевой вкладки**; канонический паттерн Chrome берёт их из `action.onClicked` прямо в SW. У нас action открывает **popup** (`openPanelOnActionClick: false`), «Начать» живёт в **side panel**, и путь `UI → sendMessage → SW` не переносит ни жест, ни грант.

Первый заход (перенос `getMediaStreamId` в UI под клик) закрыл часть кейсов, но воспроизведение пользователя уточнило корень: **грант `activeTab` появляется, только когда расширение «вызвано» на вкладке** (клик по иконке → popup → `sidePanel.open()`). Если side panel открыт **напрямую** (меню side panel Chrome, минуя иконку), гранта нет вообще — и никакой жест в UI его не заменяет, `getMediaStreamId` падает. Бесшовный захват «текущей вкладки» без гранта в Chrome невозможен в принципе (`tabCapture` требует invocation; `getDisplayMedia`/`desktopCapture` — пикер).

**Итоговое решение (два уровня, без тупиков):** (1) при наличии гранта (обычный путь через иконку) — **бесшовный** `tabCapture.getMediaStreamId` **в UI под кликом** (через seam `@/platform`), `streamId` → offscreen по `BroadcastChannel`; (2) при отказе `tabCapture` (нет гранта / любой сбой) — **автопадение на системный пикер** `desktopCapture.chooseDesktopMedia(['tab','window','screen'])`: пикер гранта не требует и работает при любом способе открытия панели. Такой поток захватывается как desktop-класс (`chromeMediaSource: 'desktop'`), поэтому звук вкладки в запасном пути не пишется (только видео + микрофон) — сознательный компромисс ради надёжности. Добавлен **предполётный отсев** заведомо незахватываемых страниц (`isRestrictedCaptureUrl` в чистом `logic.ts`: `chrome://`, страницы расширений, DevTools, Web Store). Исправлен и **порядок маппинга ошибок**: Chrome дописывает «Chrome pages cannot be captured.» и к ошибке `activeTab` на обычной странице — сигнал «не вызвано» проверяется раньше, чтобы не показывать ложное «системная страница».

**Ревизия 2026-09-20 — системный пикер `desktopCapture` перенесён из SW в UI (иначе «A target tab is required»).** Первая редакция запасного пути (и desktop-путь) вызывала `desktopCapture.chooseDesktopMedia` **в service worker'е** — на реальном Chrome это падало с `screenrec.start Error: A target tab is required when called from a service worker context.`. Корень — фундаментальное ограничение Chrome: из service worker'а `chooseDesktopMedia` **требует** параметр `targetTab` (в документе он опционален). Наивная «починка» — передать активную вкладку — некорректна: по спецификации переданный `targetTab` **привязывает поток к кадрам той вкладки, чей origin совпадает с `tab.url`**, а наш потребитель — offscreen-документ (origin расширения), поэтому `getUserMedia({chromeMediaSource:'desktop'})` в offscreen такой `streamId` уже НЕ примет (это подтверждают и репорты Chromium: desktopCapture→offscreen из SW не поддержан). Без `targetTab` поток «usable only by the calling extension» — то, что и нужно offscreen, но опустить `targetTab` можно только из **документа**. Решение: **весь `streamId` добывается в UI** (документ side panel, `requiresPanel:true` — не popup, который закрылся бы при фокусе на системном пикере) — и `tabCapture` (как раньше), и `desktopCapture.choose(...)` (теперь тоже). `screenrec/start` сузился до подготовки контекста (единственный offscreen + бейдж) и `streamId` больше не возвращает; из контракта убраны `source`/`fallbackPicker`/`desktopKind`. Порядок в UI: сначала пикер (под кликом), затем `ensure(offscreen)` — отмена пикера не создаёт лишний документ. Прав это не меняет (пикер сам по себе — согласие пользователя).

**Ревизия 2026-09-21 — экран/окно захватывается через `getDisplayMedia` ВНУТРИ offscreen («Could not build the capture stream»).** Предыдущая ревизия перенесла `desktopCapture.choose` в UI под ошибочной посылкой, что «без `targetTab` поток usable only by the calling extension и корректно потребляется offscreen». На реальном Chrome это **не так**: пользователь выбирал экран в пикере → бейдж `REC` появлялся, но запись падала с `capture-failed` → «Could not build the capture stream». Корень — задокументированное ограничение MV3: **`streamId` от `desktopCapture` привязан к запрашивающему фрейму и НЕ переживает границу документов** (side panel → offscreen); `getUserMedia({chromeMediaSource:'desktop'})` в offscreen отвергает такой id с `Invalid state`, откуда бы он ни был добыт (в отличие от `tabCapture` id, который для кросс-контекстного консюма и предназначен — [chromium-extensions](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/3RanHldyp9c)). **Решение (рекомендация Chrome для MV3):** экран/окно захватывает **сам offscreen через стандартный `navigator.mediaDevices.getDisplayMedia()`** (offscreen reason `DISPLAY_MEDIA`; нативный пикер = согласие пользователя и одновременно закрывает требование user-activation — [screen-capture docs](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)). Команда `start` теперь несёт **`CapturePlan`** — дискриминированный `{kind:'tab',streamId,tabAudio}` (бесшовная вкладка, id переживает границу) либо `{kind:'display',preferredSurface?}` (экран/окно/запасной путь; `preferredSurface`→`displaySurface`-подсказка). **Право `desktopCapture` удалено из манифеста** — `getDisplayMedia` его не требует (меньше install-warning и поверхности прав). UI на событие `error` теперь шлёт `screenrec/finalize` (снять бейдж/закрыть offscreen), т.к. пикер живёт в offscreen и его отмена приходит уже после подготовки контекста — иначе `REC` «висел» бы. Компромисс по системному звуку не меняется (desktop-аудио вне scope MVP, `audio:false`; микрофон домешивается как раньше).

**Ревизия 2026-09-22 (bugfix 6 — микрофон: запись в видимой вкладке-рекордере, а не в offscreen).** Bugfix 5 исходил из посылки (рекомендация Chrome и офиц. доки), что грант микрофона, выданный в отдельной вкладке-праймере, **персистится для origin расширения** и после этого `getUserMedia` в offscreen проходит молча. На реальном Chrome пользователя это **не подтвердилось**: вкладка-праймер открывалась, промпт показывался, пользователь разрешал доступ — и всё равно `getUserMedia` **в offscreen** падал `NotAllowedError` (в UI «Access was declined. Allow capture to record.»). Проверено вживую: грант из отдельной вкладки в offscreen **не пробрасывается** на этой конфигурации. Вывод: `getUserMedia` надёжно отдаёт микрофон **только тому документу, который сам запросил грант под жестом** — кросс-контекстная персистентность гранта на микрофон ненадёжна (в отличие от `getDisplayMedia`, которому в offscreen жест не нужен). **Решение:** запись С микрофоном ведёт **сама вкладка** (`src/features/screen-recording/recorder-tab/`), а не offscreen. По клику «Начать» в этой вкладке: `getDisplayMedia` (пикер поверхности, под жестом клика) → `getUserMedia({audio:true})` (промпт микрофона в её же контексте — работает надёжно) → `MediaRecorder`. События `state`/`progress`/`blob`/`error` идут в side panel по тому же `RECORDING_CHANNEL`; панель открывает вкладку (`tabs.create`) и закрывает её по завершении/ошибке. **Оркестратор сессии вынесен в общий `session.ts`** (одна логика записи для offscreen и вкладки — таймеры, лимит, нативный «Stop sharing», cleanup). Путь **БЕЗ микрофона не меняется** — остаётся в невидимом offscreen (там `getDisplayMedia` без жеста и без видимой вкладки). Прежняя capability `shared/mic-permission` (праймер) и страница `src/permission/mic.html` **удалены**. Прав не добавляет (`tabs.create` не требует права `tabs`; манифест — прежние `['storage','sidePanel','declarativeNetRequestWithHostAccess','debugger','offscreen']`). UX-компромисс: во время записи с микрофоном открыта видимая вкладка-рекордер (её нельзя закрывать до конца записи) и нужен один клик «Начать» в ней — цена надёжного гранта на микрофон.

**Обоснование ресёрчем (2026-09-22) — решение bugfix 6 подтверждено, iframe-в-offscreen отклонён.** После bugfix 6 проведён адверсариальный ресёрч (цель — опровергнуть выбранный путь и найти чистый «невидимый» захват с микрофоном): офиц. [screen-capture docs](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture), тред [chromium-extensions «Recording Mic/Audio from offscreen»](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/V09VMCLzvWM), запрос канонического сэмпла Google [chrome-extensions-samples #821](https://github.com/GoogleChrome/chrome-extensions-samples/issues/821), рабочий фикс [community/discussions #161632](https://github.com/orgs/community/discussions/161632). Итоги: (1) **официального «невидимого» пути записи с микрофоном не существует** — запрос канонического паттерна в репозитории Google-сэмплов открыт **без резолюции** (автор ссылается на открытые баги Chromium); (2) `getUserMedia` — permission-aware и требует UX-аффорданса промпта, которого у offscreen нет (Jackie Han, Chrome, в треде), и **никто не подтверждает надёжный проброс гранта в offscreen** — что совпадает с эмпирикой пользователя (bugfix 5 провалился); (3) **единственный путь, описанный как конкретно работающий Fix, — ровно наш**: `chrome.tabs.create()` → `getUserMedia` **в контексте вкладки** (#161632). **Явно рассмотрен и отклонён** более элегантный вариант — offscreen грузит `<iframe>` на свою extension-страницу и зовёт `getUserMedia` в нём (теоретически даёт невидимую запись с микрофоном): он (а) не имеет офиц. резолюции (#821 открыт), (б) опирается на **тот же механизм persist-гранта origin'а, который на Chrome пользователя уже сломался** (bugfix 5), (в) добавляет сложность (вложенный iframe + межконтекстный обмен потоком) ради невоспроизводимого выигрыша. **Вердикт: гибрид (микрофон в видимой вкладке) остаётся принятым решением** как единственный документированно-надёжный путь; iframe-в-offscreen — возможный будущий **эксперимент за флагом** (проверить persist-гранта именно на целевой конфигурации), но не смена архитектуры. UX-компромисс (видимая вкладка + один клик в ней) — неустранимое следствие модели прав Chrome на микрофон, а не дефект реализации.

**Ревизия 2026-09-21 (bugfix 5 — микрофон: грант в отдельной вкладке-праймере, а не в side panel). _Superseded by bugfix 6 (2026-09-22): персистентность гранта из вкладки-праймера в offscreen на реальном Chrome не сработала; запись с микрофоном перенесена в саму вкладку._** Bugfix 4 (d) праймил микрофон `getUserMedia({audio:true})` **в документе side panel** — на реальном Chrome это по-прежнему падало `NotAllowedError` **без всякого промпта** (в UI: «Microphone access was declined…», в логах `screenRecording.micPrime [object DOMException]`). Корень: **side panel — как и offscreen — не показывает системный промпт `getUserMedia`** (промпт не может закрепиться на этой поверхности), поэтому вызов отклоняется немедленно. **Решение (рекомендация Chrome для offscreen-медиа):** грант запрашивается в **одноразовой вкладке расширения** (`src/permission/mic.html`) — единственной поверхности, где промпт показывается надёжно. Вкладка зовёт `getUserMedia`, шлёт терминальный вердикт панели по `BroadcastChannel` (`MIC_PERMISSION_CHANNEL`) и закрывается; грант персистится для origin расширения, и последующий `getUserMedia` в offscreen проходит молча. Быстрый путь: если `navigator.permissions.query({name:'microphone'})` уже `granted` — вкладка не открывается. Вердикт-«отказ» приходит также при закрытии вкладки (`tabs.onRemoved`) или страховочном таймауте, чтобы не блокировать старт. Capability вынесена в **`shared/mic-permission`** (не в домен фичи): `contract.ts` — пуро-константы/тип (его импортирует лёгкая вкладка-праймер, без polyfill платформы), `broker.ts` — `ensureMicPermission` поверх платформенного seam (`tabs.create`/`tabs.remove`/`tabEvents.onRemoved`, ADR-0014). Прав не добавляет (создание вкладки права `tabs` не требует). HTML-вкладка добавлена явным входом сборки (@crxjs, как offscreen), в манифесте не декларируется.

**Ревизия 2026-09-21 (bugfix 4 — упрощение флоу, звук системы, микрофон).** Итерация упрощает пользовательский флоу и чинит две ошибки аудио, вскрытые ручной проверкой.

- **(a) Селектор источника убран — нативный пикер `getDisplayMedia` каждый раз.** Из UI удалён сегментированный контрол «Захват» (Вкладка/Окно/Экран). Любой старт записи теперь открывает системный пикер `getDisplayMedia()` («Выберите, чем поделиться…») **внутри offscreen-документа**, где пользователь сам выбирает вкладку/окно/экран при каждой записи. Поток проще и без внутреннего выбора «класса» источника.
- **(b) Бесшовный путь захвата вкладки + seam `tabCapture` + манифест-право `tabCapture` удалены (least-privilege).** Поскольку отдельного «бесшовного» пути записи активной вкладки больше нет, `chrome.tabCapture.getMediaStreamId` не используется, платформенный seam `tabCapture` снят, а **право `tabCapture` удалено из манифеста**. Итоговый `permissions` — ровно `['storage','sidePanel','declarativeNetRequestWithHostAccess','debugger','offscreen']`. Offscreen-документ по-прежнему заявляет **оба** reason'а `USER_MEDIA` (микрофон) и `DISPLAY_MEDIA` (экран/окно).
- **(c) Bugfix — системный/вкладочный звук никогда не писался.** Раньше `getDisplayMedia` вызывался с `audio:false` → звук вкладки/системы **не захватывался вовсе**. Теперь — `getDisplayMedia({ video:true, audio:<тумблер systemAudio> })`: галочка «Поделиться звуком» в пикере пишет звук вкладки (при шаринге вкладки Chrome) или системный звук (при шаринге целого экрана, на поддерживаемых ОС вроде Windows). **Loopback/monitor-узел больше не нужен** — `getDisplayMedia`, в отличие от старого `chromeMediaSource:'tab'`, источник не глушит, поэтому возвращать звук на `destination` не требуется.
- **(d) Bugfix — микрофон всегда отклонялся («Access was declined. Allow capture to record.»).** Корень: `getUserMedia({audio:true})` для микрофона вызывался **только в offscreen-документе**, который не может показать промпт разрешения → Chrome отклоняет с `NotAllowedError` → `permission-denied`. Фикс: **side panel праймит разрешение микрофона** — вызывает `getUserMedia({audio:true})` в документе панели под пользовательским жестом и сразу останавливает треки, **до** запуска offscreen-рекордера. Грант персистится для origin расширения (`chrome-extension://<id>`), поэтому последующий `getUserMedia` в offscreen проходит молча. При отказе на промпте панели показывается локализованная ошибка и запись не стартует. Микрофону по-прежнему **не нужно манифест-право** (рантайм web-permission).
- **(e) Упрощение контракта.** Типы `CapturePlan`, `RecordingSource`, `DesktopKind` удалены. Команда старта по `BroadcastChannel` теперь `{ cmd:'start', systemAudio:boolean, mic:boolean, maxDurationMs:number }`. Персистентное состояние настроек — `{ mic, systemAudio, maxDurationMs }` (ранее держало `source`/`desktopKind`/`tabAudio`).

**Ревизия 2026-09-20 — экспорт в GIF (свой чистый кодировщик).** Исходный scope помечал GIF-экспорт как «вне scope / отдельный добор». Добор реализован: к готовой записи добавлен экспорт в анимированный GIF рядом со скачиванием WebM. Ключевое решение — **свой чистый кодировщик GIF89a** (`gif.ts`, без DOM/`chrome.*`), а не сторонняя зависимость: расширение целенаправленно бездепное и локальное (ADR-0014/PRD §9), а самодельный энкодер аудируем, покрыт тестами и не добавляет supply-chain-поверхности. Он делает адаптивную палитру на кадр (медианный срез, ≤256 цветов), спец-корректный GIF-LZW (рост ширины кода + сброс словаря как в браузеро-совместимых энкодерах) и сборку байтов (зацикливание Netscape 2.0, покадровые GCE + локальные палитры). Корректность самого хрупкого места (LZW/границы подблоков/ширина кода) закреплена **round-trip тестом через независимый спец-декодер**. Планирование выборки (`planGif`: частота/потолок кадров, масштаб, задержка) — чистое в `logic.ts`; DOM-оркестратор `gif-export.ts` декодирует кадры WebM через `<video>`+`<canvas>` и кодирует **кооперативно** (уступая поток между кадрами, с прогрессом и отменой). **Worker отклонён** намеренно: бандлинг воркера в MV3/@crxjs добавляет хрупкости и CSP-поверхности, а объём кадров жёстко ограничен планом — кооперативной нарезки достаточно. Прав не добавляет; конвертация и скачивание локальны (local-privacy). Компромиссы: GIF без звука; палитровый (возможен бэндинг на фото-контенте); длинные ролики прореживаются (обзорный «таймлапс») — для точного длинного видео остаётся WebM.

## ADR-0046: In-page редактор скриншота — модальный экран событий, Paint-подпись, немедленное скачивание (ревизия ADR-0039)

**Статус:** Accepted · **Дата:** 2026-09-22

**Контекст.** Отчёт пользователя по in-page («заморозка экрана») редактору TASK-035/ADR-0039: при добавлении инлайн-подписи на снимок «начинаю писать — и клики/клавиши проходят сквозь скрин, на странице триггерятся ивенты». Корень — устройство модального барьера оверлея. Интерактивные части (кнопки тулбара, поле подписи) живут в **закрытом Shadow-DOM** и обязаны получать нативные жесты, поэтому capture-барьер на `document` их сознательно пропускает (`return` без `stopPropagation`). Но события *composed*: пройдя целевой узел в shadow, они **всплывают наружу** к делегированным `document`/`window`-слушателям «замороженной» страницы (роутеры SPA, глобальные горячие клавиши, «клик мимо», аналитика) — оттого клики и набор текста в подписи достигали страницы. Вдобавок барьер перехватывал только события мыши — указатель/тач не гасились вовсе. Попутно вскрылись два расхождения с side panel: подпись вводилась во встроенном в тулбар инпуте + кнопке «Поставить» (не Paint-стиль «в точке клика»), а скачивание требовало подтверждения (баннер `confirmRow`), хотя в side panel баннер уже снят.

**Решение.** (1) **Модальный экран событий на границе `host`.** Единый обработчик `shieldFromPage` вешается на shadow-`host` в фазе **всплытия** для полного набора пользовательских событий (`SHIELDED_EVENTS`: pointer/mouse/wheel/touch/keyboard/clipboard/drag/focus) и вызывает только `e.stopPropagation()`. Точка выбрана осознанно: перехват в capture на `document` (корень) остановил бы событие **до** целевого узла оверлея и сломал бы ввод; барьер на `host` в фазе всплытия срабатывает **после** обработки узлом оверлея, но **до** выхода в документ страницы. Так как все узлы оверлея — потомки `host`, один механизм кроет холст, тулбар и поле подписи для всех типов событий. Только `stopPropagation`, **никогда `preventDefault`** — фокус/каретка/ввод/paste в подписи работают штатно; `stopImmediatePropagation` не берём (не гасить собственные со-слушатели узла). Дополняется capture-барьером производных от указателя (`onPointerBarrier`: `click`/`dblclick`/`auxclick`/`contextmenu`). Регистрация и снятие симметричны в `finish()` — без осиротевших слушателей. (2) **Paint-подпись** — плавающий `position: fixed` инпут в точке клика по выделению (печать на месте, фиксация Enter/blur, отмена Esc; guard `if (settled) return` в `placeText()` защищает от осиротевшей подписи при teardown). (3) **Немедленное скачивание** — баннер подтверждения удалён (подписи `confirm`/`confirmDownload`/`place` сняты); PNG скачивается сразу, как в side panel.

**Следствия.** (+) Оверлей стал полноценной **модальной ловушкой ввода**: клики и клавиши не протекают на страницу под ним ни для одной модели событий (мышь/указатель/тач/клавиатура/буфер/drag), при этом ввод подписи полностью работоспособен. (+) Обе поверхности (side panel и in-page) ведут себя одинаково: Paint-подпись в точке и скачивание без лишнего клика. (+) Прав/сети не добавляет; экспорт остаётся локальным, замазка деструктивна, автоотправки нет — снятие confirm убирает источник, а не расширяет поверхность. (−) **Остаточный край, неустранимый без iframe:** capture-слушатели, повешенные страницей на `document`/`window` **до** открытия оверлея, ловушкой на `host` не гасятся (они видят событие в capture, ещё до всплытия к host) — редкий случай; симптом отчёта (всплытие/делегирование) закрыт полностью. Радикальное лекарство — вынести оверлей в изолированный iframe (отдельная задача, если встретятся страницы с агрессивным capture-перехватом). (−) Сам `screenshot-editor.ts` (in-page оверлей) юнит-теста не имеет (тулбар/поле в **закрытом** Shadow-DOM недоступны из jsdom, как отмечено в ADR-0039) — правки покрыты typecheck + разбором фаз событий; ручная проверка на реальном SPA — обязательный шаг приёмки. **Ревизует ADR-0039:** пункт «скачивание только с подтверждением» снят; модальный экран событий и Paint-подпись добавлены к его инвариантам (инвариант TASK-013 «без мутаций DOM» и общий `draw.ts` — без изменений).

## ADR-0047: Ленивая загрузка тел фич + расцепление UI/background барелей (перф, TASK-046)

**Статус:** Accepted · **Дата:** 2026-09-28

**Контекст.** Аудит производительности (2026-09-23) показал одну корневую неэффективность в нескольких местах: единый чанк **560 КБ** (min) со всеми 20 фичами грузился жадно всеми точками входа — popup, sidepanel, service worker И offscreen-документом, — хотя каждой нужна лишь часть. Корень — барель `@/features`: он импортировал `index.ts` каждой фичи, а тот статически тянул своё тело `ui.tsx` (+ логику/zod/canvas), контракты сообщений и background-хендлеры. В результате popup грузил тела всех фич и фоновой код (перехватчики сети, DNR/CDP, replay-sender, offscreen-оркестрацию), а SW — весь UI-граф с preact-render-кодом. Расширение local-first: весь этот вес — клиентский CPU/RAM на машине пользователя. Отдельно: MAIN-перехватчик мока (`interceptor.ts`) строил `new RegExp(...)` в `matchRule` на КАЖДЫЙ перехваченный fetch/XHR (тип назван `CompiledRule`, но regex не прекомпилировался).

**Решение.**
1. **Ленивое тело фичи (F1).** Поле дескриптора `Component` заменено на ленивый загрузчик `load: () => import('./ui').then((m) => m.XPanel)` (`FeatureLoader`, `registry.ts`). Метаданные (id/title/category/icon/order/surface/permissions/messages/content) регистрируются ЖАДНО, тело (`ui.tsx` + его зависимости) резолвится динамическим `import()` при первой активации фичи. Оболочка рендерит его через `LazyPanel` (`src/ui/shell`) с контролируемыми состояниями: короткий спиннер без сдвига layout, мягкая деградация при сбое импорта (сообщение + «Повторить»), модуль-кэш резолвленных тел (повторное открытие — мгновенное).
2. **Расцепление барелей (F2/F6).** Введён отдельный background-барель `@/features/background`, который импортирует ТОЛЬКО SW-сторону фич (background-хендлеры + контракты сообщений) и регистрирует хендлеры в отдельном реестре (`registerBackground`/`allBackgroundHandlers`). Service worker (`background/index.ts`) импортирует его вместо `@/features` — и больше не тянет ни одного `ui.tsx`/preact. UI-дескрипторы фич больше не несут `backgroundHandlers`; поле снято с `FeatureModule`.
3. **Контракты сообщений остаются жадными на обеих поверхностях** — сознательно. Протокол сообщений — federated contracts (ARCHITECTURE §5): фича может слать сообщение, чей контракт объявлен в другой фиче (напр. «Экспорт бага» шлёт `mock/poll`). Таблица контрактов — глобальная и не зависит от того, какие тела фич загружены. Поэтому ленивым делается только тело, а `defineMessage` (zod-схемы) регистрируются жадно и в UI-бареле (через `index.ts` → `./messages`), и в background-бареле.
4. **Прекомпиляция regex мока (F5).** `installMockInterceptor` компилирует `RegExp` каждого правила ОДИН РАЗ при построении/обновлении стора (`compileRegexes`, хранится в `MockStore.compiled` параллельно `rules`), `matchRule` переиспользует готовый regex. Семантика матчинга идентична: невалидный паттерн → `null` → не матчится (как прежний try/catch, но ошибка ловится на этапе компиляции). Функция остаётся самодостаточной для MAIN-инъекции (ADR-0028): хелпер объявлен внутри тела.

**Следствия.** (+) Замер по vite-манифесту (до → после): popup **605.9 → 313.7 КБ** (−48%), sidepanel **603.2 → 304.3 КБ** (−50%), **service worker 576.2 → 126.5 КБ** (−78%, ноль `ui.tsx` в статическом графе), offscreen **574.8 → 252.9 КБ** (−56%); все 20 тел фич — отдельные on-demand чанки, приходят при открытии. (+) F5 убирает O(правил) компиляций regex с каждого перехваченного запроса. (+) **Инвариант расширяемости сохранён** (ARCHITECTURE §1, §13): добавление фичи = одна строка в UI-бареле `@/features`; фича с фоновыми хендлерами — плюс одна строка в `@/features/background`. Ядро (`background/index.ts`, popup/sidepanel) не редактируется под конкретную фичу. Fitness-инвариант §12 расширен: (1) разрешает барели `@/features`/`@/features/background`/`@/features/registry` как точки агрегации; (7) стражит расцепление — SW тянет только background-барель, UI-барель не тянет фоновой код, дескрипторы не импортируют `./ui` статически. (−) Наблюдаемое поведение фич не меняется, но добавляется одно новое состояние UI — короткий fallback тела при первой активации (спиннер/ошибка загрузки). (−) **F3 (zod ~149 КБ) остаётся вне scope:** контракты сообщений жадны by design (см. п.3), поэтому zod-схемы `messages.ts` каждой фичи остаются в жадном графе UI/SW; их вынос требует отдельного решения (напр. `zod/mini` — апгрейд уровня тимлида). F4 (host инспекции) не трогали. Права (`PERMISSIONS.md`) не менялись — перф-задача не расширяет поверхность прав.

**Альтернативы.** (а) `lazy`+`Suspense` из `preact/compat` вместо своего `LazyPanel` — отклонено: нужен полный контроль над состояниями загрузки/ошибки (Suspense-error-boundary в preact/compat слабее) и модуль-кэшем. (б) Оставить один барель и полагаться на то, что ленивый `Component` уберёт UI из графа SW «автоматически» — отклонено в пользу явного background-барреля: он даёт чистый SW-граф (без preact/icons/i18n) и делает инвариант «UI-барель ≠ background-барель» проверяемым (fitness §12.7). (в) Прекомпилировать regex в SW и передавать в перехватчик — невозможно: `RegExp` не переживает сериализацию `func.toString()` в MAIN-world (ADR-0028), поэтому компиляция вынесена внутрь стора перехватчика.

## ADR-0048: Профили сессий — local-first hot-swap авторизации поверх снимков TASK-017; оркестрация на поверхности, без нового контракта; секреты не синкаются (TASK-047)

**Статус:** Accepted · **Дата:** 2026-09-28

**Контекст.** Частая рутина ручного QA — переключение между учётками/ролями на одном сайте (admin/manager/user/guest) через logout→login по кругу. Нужна фича «Профили сессий»: сохранять именованные профили сессии для сайта и переключаться одним кликом, делая hot-swap состояния авторизации (cookies + localStorage + sessionStorage). Принцип пользователя — «всё необходимое добавляет он сам» (снимает текущую сессию или вводит токены руками), расширение только сохраняет и применяет (swap). Фундамент уже заложен редактором состояния (TASK-017): сериализуемый `StorageSnapshot`, RPC `storage/*` (content-target) и `cookies/*` (background-target, `chrome.cookies` умеет `HttpOnly` — где живёт большинство реальных сессионных токенов), `diffSnapshot`, `validateCookieAttrs`, `buildCookieUrl`. Ресёрч OSS-свитчеров (Session Swap/Shift, CookieSwapper, Local Session Switcher) даёт общий паттерн «применить набор + подрезать устаревшее + reload», local-first, без облака; проприетарный SessionBox берёт параллельными сессиями, но требует аккаунт и синкает данные на сервер — анти-паттерн приватности PRD §9.

**Решение.**
1. **Профиль = именованный артефакт**, привязанный к области сайта (`origin` + `cookieDomain`) и содержащий `StorageSnapshot` (переиспускается схема снимка TASK-017, не дублируется). Хранение — версионированный конверт (`kind: 'session-profile'`, `schemaVersion`, хук миграций) для экспорта/импорта.
2. **Чистое ядро `logic.ts`** (≈100% покрытие, без DOM/chrome/preact): сборка снимка из read-RPC, `buildSwapPlan(current, target, mode)` с режимами `replace` (prune-then-apply, дефолт) и `apply` (аддитивный), матч области (`scopeCompatibility`), маскирование значений, конверт экспорта, иммутабельные CRUD-хелперы коллекции.
3. **Оркестрация свапа — на стороне ПОВЕРХНОСТИ (`swap.ts`, вызывается из `ui.tsx`), а НЕ через новый background-хендлер `profiles/apply`** (осознанное отклонение от исходного плана задачи). Причина: применить web storage можно только в content-мире; из фонового хендлера фичи это потребовало бы либо связать фичу с `@/background/inspection` (обратная зависимость `features → background`, против ARCHITECTURE §3), либо продублировать путь инъекции/форвардинга. Поверхность же уже умеет всё нужное — те же RPC, что использует `applyImport` редактора состояния (TASK-017): `cookies/*` идут в background→`chrome.cookies` (включая `HttpOnly`), `storage/*` генерически форвардятся в content с инъекцией хоста. Порядок применения — prune → apply → reload. `swap.ts` пишется с инъектируемыми зависимостями (тестируем без Chrome), отчёт `applied/removed/failed` едет данными (`Result`), не throw.
4. **Reload вкладки после свапа** — новый платформенный seam `tabs.reload` (`browser.tabs.reload`, ADR-0014). Обязателен: SPA/приложение перечитывает сессию только при загрузке документа. Фолбэк-ветка не понадобилась — `tabs.reload` доступен при host-доступе.
5. **Никаких новых контрактов/прав.** Фича НЕ переобъявляет `storage/*`/`cookies/*` (иначе дубль id — падение architecture-fitness §12.3), не имеет собственных `messages`/`backgroundHandlers`/`content`. Права (`scripting` + `cookies` + host `*://*/*`) — те же optional, что у TASK-017; новых install-прав нет, брокер запрашивает под жестом (ADR-0013). Отказ в `cookies` не роняет фичу — деградация до web storage.
6. **Приватность.** Профили хранятся только в `chrome.storage.local` (namespace `session-profiles`) и НИКОГДА не синкаются (добавлены в `DEFAULT_EXCLUDED_NAMESPACES`, прецедент секретов TASK-029/017). Значения маскируются по умолчанию (тумблер «показать»); честное предупреждение о local-trust (не имитируем шифрование, которого нет). Перенос между стендами — только ручной экспорт/импорт файла (диф-предпросмотр перед применением).

**Следствия.** (+) Инвариант расширяемости соблюдён строго: добавление фичи = одна строка в UI-бареле `@/features` + переиспользование существующего слоя; ни background-барель, ни реестр сообщений, ни манифест, ни content-бандл не редактируются. (+) Нулевой прирост поверхности прав и контрактов → нулевой риск для fitness §12.3/§12.6. (+) `HttpOnly`-cookie — реальный дифференциатор против DevTools/скриптов (их пишет только `chrome.cookies` из background). (−) Свап не «атомарен на уровне SW»: если поверхность закрыть в момент применения, цикл прервётся; митигируется тем, что reload — последний шаг, а отчёт показывает фактически применённое; это тот же принятый компромисс, что у `applyImport` TASK-017. (−) MVP — **последовательный** swap (одна активная сессия на сайт), НЕ параллельные изолированные сессии по вкладкам (Chrome не даёт чистый per-tab cookie-store) — заведено отдельной задачей в бэклог. Вне MVP также: IndexedDB/Cache как место токенов (добор поверх TASK-031), авто-логин/refresh, шифрование at-rest.

**Альтернативы.** (а) Background-хендлер `profiles/apply` (исходный план задачи) — отклонён по причине из п.3 (обратная зависимость `features→background` / дублирование инъекции ради мнимой атомарности, которую MV3-SW всё равно не гарантирует — воркер может быть убит). (б) Параллельные сессии через контейнеры/`cookieStoreId` — вне возможностей стабильного API расширений без Firefox-контейнеров; отдельная крупная задача. (в) Шифрование профилей мастер-паролем (WebCrypto) — отложено: local-trust — принятая модель всех OSS-свитчеров; кандидат на добор при спросе, зафиксирован как открытый вопрос. **Закрыт ADR-0051 (TASK-050)** — добавлено опциональное at-rest-шифрование (PBKDF2/AES-GCM, ключ только в памяти).

## ADR-0049: Навигация по DOM-иерархии как stateful-команда над якорем (без переноса DOM-узлов через границу сред) — TASK-052
**Статус:** Accepted · **Дата:** 2026-09-29

**Контекст.** Инспекционный слой (TASK-013) выбирает **один** узел (`event.target` под курсором) и держит его как «якорь» `lastPicked` в content-хосте; `collect`/`scan` работают относительно него. Навигации по дереву не было: под курсором почти всегда листовой узел (иконка, `<span>`), а инспектировать нужно контейнер (карточку, кнопку, секцию) — или, наоборот, спуститься. Единственный способ сменить цель — заново прицелиться мышью, что неточно на плотной вёрстке и невозможно для узлов без площади (нулевой размер, `display:contents`, перекрытые оверлеем). DevTools решают это стрелками ↑/↓ и breadcrumb-путём предков. Нужен эквивалент во всех `inspector-*`, **переиспользуя** слой (пикер/права/сессии), а не дублируя логику в каждой фиче. Жёсткий инвариант TASK-013 (PRD 6/9/10): DOM-узлы **не пересекают** границу сред — наружу ходят только сериализуемые снимки; DOM страницы не мутируется (оверлей в closed Shadow DOM); least-privilege (новых прав не вводим).

**Решение.**
1. **Навигация — команда над якорем, а не «отдать узел в UI и навигировать там».** DOM-узлы несериализуемы и по инварианту не пересекают границу. Единственный держатель «текущего элемента» — content-хост. Поэтому UI шлёт `inspection/navigate(step, depth?)`, а host применяет `resolveStep` к `lastPicked`, **обновляет якорь**, перерисовывает подсветку оверлея и `scrollIntoView` на новый узел и возвращает наружу только снимок-состояние `NavigationState` (дескрипторы, не ссылки). Это же даёт бесплатно синхронную подсветку (host рядом с DOM).
2. **Чистая модель `shared/inspection/navigation.ts`** (без chrome/preact, jsdom-≈100%): `resolveStep` (`parent`/`firstChild`/`next|previousSibling`/`ancestorAtDepth`), `describeNode`, `buildPath` (breadcrumb с усечением «с середины» по бюджету — глубокие деревья не раздувают ответ; каждый дескриптор несёт настоящую `depth`, поэтому клик по предку остаётся адресным после усечения), `navigationState`.
3. **Единый предикат «значимости» `isInspectableElement` в `dom.ts`** — один источник правил для обхода `walk` и навигации: пропускаются собственный оверлей (`[data-qatb-overlay]` и его поддерево), служебные нерендеримые теги (`script`/`style`/…), `display:none`. Так обход и навигация не расходятся (требование ТЗ §4).
4. **Аддитивное расширение контрактов.** `inspection/pick` теперь возвращает снимок узла **надмножеством** `PickedElement` + `navigation`-состояние (панель рисует breadcrumb без лишнего round-trip; старые потребители — ruler A/B, palette eyedropper — по-прежнему читают `selector`/`rect`/`tagName` с верхнего уровня). Новый `inspection/navigate` (`target: content`, zod на обеих границах). Дубли id сборщиков/сообщений не вводятся (fitness §12.3).
5. **Общий UI-слой `src/ui/inspection`.** Хук `useInspectedNode` — **единственный** носитель ранее скопированного по фичам потока (ленивый брокер прав + `ensure` под жестом, `tabs.queryActive`, `pick`, `navigate`, авто-`collect` сборщика фичи после каждого шага, session-token против гонок, `busy`/`error`, `Esc`/«Отмена» + best-effort `teardown`, клавиатура ↑/↓/←/→). Компонент `HierarchyNav` — чистое представление `NavigationState` (breadcrumb + шаговые контролы, `aria-current`, disabled по `canAscend`/`canDescend`/границам соседей). Все пять `inspector-*` подключают их вместо своей копии логики; контраст получил **новый** режим «Осмотреть элемент».
6. **Деградация без исключений.** Нет якоря → `null`; невозможный шаг (нет родителя/детей/соседа) → текущее состояние без смены якоря (идемпотентно); якорь удалён из DOM (SPA-перерисовка, узел вне `document`) → безопасный `null` со сбросом якоря, а не throw. Зажатая стрелка коалесится (single-flight + последний шаг), RPC не копятся.

**Следствия.** (+) Инвариант границ сред соблюдён строго — наружу только снимки; синхронная подсветка бесплатна. (+) Устранено дублирование: pick/permissions/session/teardown жили в 5 местах, теперь один хук — это и есть prod-ready результат задачи, а не «ещё одна кнопка». (+) Новых прав/манифеста/бандла не трогаем; `navigate` форвардится генерически (background не упоминает конкретный тип). (+) Единый предикат значимости исключил риск расхождения обхода и навигации. (−) Навигация ограничена light-DOM текущего документа: проход сквозь Shadow DOM/внутрь `<iframe>`/псевдоэлементы и hover-time drill вынесены в бэклог (TASK-053). (−) SPA-фолбэк к «живому предку» на практике почти всегда даёт `null` (у отсоединённого узла `parentElement` уже `null`) — это честная безопасная деградация, не потеря функциональности.

**Альтернативы.** (а) Отдавать сериализованное дерево/поддерево в UI и навигировать там — отклонено: несовместимо с инвариантом «DOM не пересекает границу», раздувает ответ, рассинхронит подсветку. (б) Копировать навигацию в каждую фичу — отклонено: множит дублирование, которое задача как раз должна убрать. (в) Полноценный tree-view-панель вместо breadcrumb — вне scope (заведено доборами в TASK-053).

## ADR-0050: Живой режим инспекции как персистентная content-сессия + pick-loop в UI (без push-канала content→панель) — TASK-056
**Статус:** Accepted · **Дата:** 2026-10-01

**Контекст.** TASK-013/TASK-052 дали одноразовый выбор: `inspection/pick` резолвится по **первому** клику, host запоминает узел как единственный якорь `lastPicked`, дальше цель меняется только стрелками/breadcrumb (`inspection/navigate`). Чтобы провалиться в соседнее поддерево, нужно заново жать «Выбрать элемент» и целиться мышью. Это расходится с эталонами (Chrome DevTools inspect-mode, Vue DevTools, Figma Dev Mode), где режим инспекции **живёт**: курсор непрерывно подсвечивает элемент под собой, а клик по вложенному проваливает внутрь, не выходя из режима. Пользователь зафиксировал развилки: (1) после клика режим **остаётся живым** (выход — `Esc`/тумблер), (2) эталон компонентного уровня — Vue DevTools. Жёсткий архитектурный крюк: шина строго **request → один response** (`chrome.runtime.sendMessage` + `sendResponse`), push-канала content→панель нет — «каждый клик сам присылает панели новое состояние» одним сообщением невозможно. Инварианты TASK-013/ADR-0049 сохраняются: DOM-узлы не пересекают границу сред; DOM страницы не мутируется (оверлей в closed Shadow DOM); least-privilege (новых прав нет).

**Решение.**
1. **Персистентная live-сессия в content-хосте + pick-loop в хуке (без нового транспорта).** Host держит ПОСТОЯННУЮ сессию инспекции: смонтированный оверлей, `cursor: crosshair`, непрерывный `mousemove` → hover-подсветка, обработчики `click` и `Esc` (все — в capture-фазе на `document`, клик по странице гасится, собственный оверлей `[data-qatb-overlay]` исключён). Новый `inspection/pickLive` резолвится на **очередном** клике снимком кликнутого узла (`NavigationState`, попутно `lastPicked = target`), но **сессия остаётся смонтированной**. Панель ставит `state`, пересобирает `collect` и **сразу пере-вооружает** `pickLive`.
2. **Подсветка под курсором принадлежит сессии, а не отдельному `pickLive` — это и устраняет flicker.** Пере-вооружение только переустанавливает next-click-резолвер; оверлей/crosshair/`mousemove` не пересоздаются. Гарантия проверяется юнитом (счётчик хостов оверлея = 1 между кликами) и e2e/живой проверкой.
3. **Буфер последнего клика.** Если клик пришёл в окно между резолвом и пере-вооружением — он буферизуется и отдаётся следующему `pickLive` немедленно, чтобы быстрый повторный клик не потерялся.
4. **Два состояния оверлея.** `locked` (сплошной синий бокс = выбранный узел) и `hover` (отдельный, пунктир/светлее = под курсором) в одном closed Shadow DOM; `highlight(rect, variant?)` по умолчанию рисует `locked` (обратная совместимость: `navigate`/`highlight`/одноразовый `pick` не тронуты). `navigate`/стрелки обновляют `locked` на новом якоре — клавиатура и курсор живут в одном оверлее.
5. **Выход из live сохраняет узел.** `Esc` на странице / `inspection/pickLiveStop` из панели / session-token в хуке резолвят ожидающий `pickLive` как `null`; хук трактует `null` как «выйти из live, **сохранив** последний осмотренный узел» (панель не гаснет, степпер продолжает работать). Полное закрытие (`inspection/teardown`/`pagehide`) по-прежнему снимает оверлей и забывает якорь.
6. **Аддитивность.** Одноразовый `inspection/pick` и его потребители (ruler A/B, пипетка палитры) не тронуты — live включается **только** для навигируемого «Инспектора элемента»/probe. Обратная подсветка панель→страница переиспользует существующий `inspection/highlight` (по селектору), новый RPC не вводится. Дубли id сборщиков/сообщений не вводятся (fitness §12.3).

**Следствия.** (+) UX-паритет с DevTools/Vue DevTools без изменения транспорта: «loop + персистентная сессия» эквивалентна push-стриму по ощущению. (+) Нет flicker между кликами (hover принадлежит сессии). (+) Инвариант границ сред и «DOM не мутируется» соблюдены строго; новых прав/манифеста нет; `pickLive`/`pickLiveStop` форвардятся генерически. (+) Курсор — инструмент **спуска**; подъём к перекрытому родителю и переходы по соседям — через степпер `HierarchyNav` (TASK-052), который поэтому остаётся обязателен (курсором в полностью закрытого детьми родителя не попасть). (−) Курсором нельзя подняться к перекрытому родителю — фундаментальное ограничение hover-инспекции, компенсируется степпером. (−) Обратная подсветка по `node.selector` не всегда уникальна (подсветится первый матч) — осознанный компромисс для визуальной подсказки. (−) Проход сквозь Shadow DOM/`<iframe>`/псевдоэлементы и hover-time drill до клика остаются в TASK-053 (вне scope).

**Альтернативы.** (а) Push-канал content→панель (WebSocket-подобный стрим кликов) — отклонено: вводит новый транспорт ради UX, который достижим без него; «loop + персистентная сессия» эквивалентна. (б) Ремонтировать оверлей/слушатели на каждый `pickLive` — отклонено: даёт мигание между кликами. (в) Выходить из режима после каждого клика (чистый DevTools) — отклонено пользователем в пользу «остаётся живым» (Vue-DevTools-паттерн). (г) Двойной клик как «на уровень внутрь» (Figma-механика) — необязательный последующий добор, заведён в бэклог.

## ADR-0051: Профили сессий — опциональное at-rest-шифрование мастер-паролем (PBKDF2-HMAC-SHA256/AES-GCM-256, ключ только в памяти, версионированные параметры) — TASK-050

**Статус:** Accepted · **Дата:** 2026-10-03

> **Назначение (строго одно).** Фича решает **ровно одну** задачу: чтобы сохранённые профили-секреты **не лежали открытым текстом** в `chrome.storage.local`. Это защита **данных в покое (at-rest)** и ничего больше. Она **не** повышает безопасность живой сессии: разблокированный сейф держит ключ в памяти, а применение профиля (hot-swap) всё равно пишет открытые токены в живые cookies/страницу. Модель — как у vault менеджера паролей: заблокирован → на диске шифротекст; разблокирован → данные доступны. Против атакующего, уже находящегося в работающем браузере (кейлоггер, malware/другое расширение в активной сессии), фича не даёт ничего — и не должна. Подробные границы — в пункте 7 ниже.

> Нумерация: файл задачи планировал ADR-0053 (в предположении, что доборы профилей TASK-048→ADR-0051 и TASK-049→ADR-0052 лягут раньше). На момент выполнения последний ADR — 0050, поэтому по правилу «следующий свободный номер» присвоен **ADR-0051**. Закрывает открытый вопрос **ADR-0048 (в)**.

**Контекст.** Профили сессий (TASK-047) содержат **живой авторизационный материал** — cookies (в т.ч. `HttpOnly`), токены в `localStorage`/`sessionStorage` — и лежат в `chrome.storage.local` **открытым текстом**. Это осознанная «local-trust»-модель (ADR-0048), честно задекларированная предупреждением в UI. ADR-0048 (в) оставил открытым вопрос шифрования мастер-паролем «на WebCrypto, без зависимостей». Угроза, которую нужно закрыть: украденный/эксфильтрированный дамп `chrome.storage.local` (другим расширением, malware по диску, при краже устройства «в покое») сегодня читается без усилий. Жёсткие инварианты: ноль новых рантайм-зависимостей (ADR-0007/0014), чистая логика отдельно от I/O (ADR-0004), секреты не синкаются (ADR-0037/0048), расширяемость без правок ядра (ADR-0047).

**Ресёрч (независимо верифицирован, 2026-10-03, первоисточники).** WebCrypto **не** даёт Argon2id/scrypt — только PBKDF2 (`SubtleCrypto.deriveKey`); Argon2id-в-WebCrypto существует лишь как **не-shipping WICG-черновик** (2026). OWASP Password Storage Cheat Sheet (актуально 2025/2026): **PBKDF2-HMAC-SHA256 — 600 000 итераций**. NIST SP 800-38D: AES-GCM требует **уникального 96-битного IV на запись** (nonce-reuse катастрофичен), 128-битный auth-tag даёт целостность/tamper-detection (отдельный HMAC не нужен). Производный ключ держится **только в памяти** (`extractable:false`); MV3 SW убивается по простою — ключ теряется, принятый паттерн — повторный unlock + auto-lock, **не** персист ключа (в т.ч. не в `chrome.storage.session`). Verifier-canary (шифровка известной константы) — стандартный приём быстрого отличения неверного пароля без расшифровки всех записей.

**Решение.**
1. **Опциональность — жёсткий инвариант.** Дефолт не меняется: open/local-trust, существующие профили TASK-047 читаются без пароля. Схема настроек читает обе формы профиля — открытую (`snapshot`) и зашифрованную (`enc`) через `PersistedProfileSchema` (`z.union`); `vault?` в состоянии = «сейф включён». Включение/выключение — явные миграции под подтверждением.
2. **Бездепный крипто-набор** (переиспользуемый `shared`-модуль, не встроенный в фичу): **PBKDF2-HMAC-SHA256, 600 000 итераций, соль 16 Б/сейф → AES-GCM-256, IV 12 Б/запись (свежий на каждый `seal`), verifier-canary**. Пер-профильное шифрование снимка (у каждого свой IV), метаданные (`name`/`scope`/`createdAt`/`updatedAt`) — открыты (список и группировка видны в залоке).
3. **Чистое/I-O разделение.** `shared/crypto/vault.ts` — ЧИСТО: типы+zod конвертов (`VaultDescriptor`/`EncryptedRecord`), константы, `needsRekey`, base64-кодеки, парсеры (не бросают, коды `invalid-shape`/`unsupported-version`), хук миграций. `shared/crypto/subtle.ts` — тонкий seam над `crypto.subtle` (`deriveKey`/`seal`/`open`/`newSalt`/`makeVerifier`/`verifyPassword`) с **инъекцией источника байт** → детерминированные тесты (фиксированные соль/IV; round-trip, неверный пароль, tamper, свежесть IV). Оркестрация — `features/session-profiles/vault-store.ts` (держатель ключа в памяти + auto-lock, enable/disable/rekey, обёртки шифр/расшифр), пишет новый блоб namespace ЦЕЛИКОМ одним `set` (атомарность на уровне записи настроек).
4. **Ключ только в памяти, `extractable:false`.** Не пишется в storage, не ходит по шине, не логируется; пароль не сериализуется и не попадает в текст ошибок. Auto-lock по таймауту (настраиваемо, дефолт 15 мин) + кнопка «Заблокировать»; убитый SW/перезапуск → `locked` → повторный unlock перед действием с секретами (не throw — типизированный `Result`).
5. **Версионируемость.** KDF-параметры — в `VaultDescriptor` (не зашиты в код); `needsRekey` при заниженных итерациях → прозрачный ре-кей (расшифровать старым ключом, зашифровать текущими параметрами, свежая соль). `schemaVersion` конверта — с хуком миграций.
6. **Экспорт/импорт.** **Ранжированное решение:** по умолчанию экспорт — **расшифрованным JSON с явным подтверждением** (сохраняет сценарий переноса между стендами из TASK-047; файл честно помечен как открытый). Экспорт, зашифрованный отдельным share-паролем (портируемый конверт) — **осознанно отложен в бэклог**: вторая KDF-поверхность с малой выгодой над существующим сценарием; вводить без спроса — против принципа «не множить поверхность».
7. **Честная модель угроз в UI и ADR (дословно).** ✅ Защищает: украденный/скопированный дамп `chrome.storage.local`, кража «в покое». ❌ НЕ защищает: кейлоггер; malware/другое расширение в **разблокированной** сессии (ключ в памяти → оракул шифр/дешифр); тот факт, что hot-swap **всё равно пишет открытые токены** в живые cookies/страницу; слабый мастер-пароль (PBKDF2 лишь замедляет перебор). **Нет recovery** (zero-knowledge): забытый пароль = потерянные данные, никаких бэкдоров/резервных вопросов.
8. **Приватность неизменна.** `session-profiles` остаётся в `DEFAULT_EXCLUDED_NAMESPACES` — не синкается ни в открытом, ни в зашифрованном виде; перенос — только ручной файл. Новых прав/контрактов сообщений фича не вводит (шифрование — локальная трансформация хранения).

**Следствия.** (+) Украденный дамп storage без пароля — нечитаемый шифротекст с проверкой целостности. (+) Бездепно, аудируемо, по OWASP-2026/NIST; крипто-примитив переиспользуем (`shared/crypto`). (+) Обратная совместимость: дефолт-поведение TASK-047 не изменилось. (+) Чистый слой ≈100% покрыт детерминированными тестами (фиксированные соль/IV). (−) PBKDF2 слабее memory-hard Argon2id против GPU/ASIC — осознанный бездепный компромисс (Argon2 в WebCrypto ещё не shipping); при появлении требования — отдельный ADR + миграция (параметры уже версионированы). (−) Защита только at-rest: в разблокированной сессии и при применении профиля секреты доступны — заявлено честно, не имитируем большего. (−) Забытый пароль необратим (цена zero-knowledge).

**Альтернативы.** (а) **Argon2id/scrypt через wasm** — криптографически сильнее, но добавляет рантайм-зависимость и supply-chain-поверхность (против ADR-0007); **отклонено**, при спросе — отдельный ADR (заведено в бэклог). (б) **Шифрование всего namespace одним конвертом** — проще, но теряет «список виден в залоке» и мелко-гранулярную устойчивость (один IV на всё) — **отклонено**. (в) **Персист ключа в `chrome.storage.session`**, чтобы пережить перезапуск SW — **отклонено**: читается другими контекстами расширения и живёт до конца сессии браузера, что сводит на нет auto-lock и расширяет экспозицию (верифицировано ресёрчем). (г) **WebAuthn/passkey-разлочка сейфа** — отдельная крупная задача, в бэклог.

**Addendum (2026-10-03, UX-доработка по ревью).** Без изменения крипто-контракта, усилен безопасный UX необратимой операции: (1) предупреждение `noRecovery` показывается **в форме включения** (до коммита) + обязательный чекбокс-подтверждение, **гейтящий** кнопку «Включить» — раньше предупреждение всплывало лишь после включения; (2) индикатор надёжности сделан **устойчивым к парольным фразам** (длина доминирует: длинная фраза = `strong`, а не `fair`/«длиннее») — прежняя эвристика по классам символов толкала к коротким «сложным» паролям; (3) **показать/скрыть** на всех полях пароля (опечатка в zero-knowledge-пароле иначе необратима), Enter-сабмит всех форм, цветная полоска надёжности, подсказка диапазона auto-lock, деструктивное «Отключить» — под раскрытие. (4) **Реактивность:** мутации сейфа возвращают записанное состояние, UI отражает его в сигнал оптимистично (без повторного чтения storage) — статус меняется мгновенно и не зависит от доставки `storage.onChanged` (это также делает переходы сейфа демонстрируемыми в dev-preview, где событие заглушено). Инвариант «ключ только в памяти, пароль не сериализуется» не затронут.

## ADR-0052: Matched CSS rules / каскад — чистый обход CSSOM в content-скрипте, а не CDP (`debugger`) — TASK-055

**Статус:** Accepted · **Дата:** 2026-10-03

**Контекст.** TASK-054 превратила «Инспектор элемента» (`probe`) в сводную карточку **вычисленных** свойств узла (`getComputedStyle`), отвечая «что применено». TASK-055 закрывает «почему именно это»: какое CSS-правило задало свойство, какой селектор победил в каскаде, что перекрыто, из какого источника (стайлшит/inline). Matched rules — классический «DevTools-уровень», и у него два принципиально разных способа добычи. Инварианты слоя (TASK-013/ADR-0049/0050): сборщик — ЧИСТЫЙ модуль `shared/inspection/**` (без `@/content/**`/`preact`/`chrome.*`, fitness §12.1/§12.2/§12.5), источники инъектируются для jsdom; DOM-узлы и `CSSRule`-объекты НЕ пересекают границу сред (наружу — сериализуемый снимок); DOM страницы не мутируется; внешней сети нет; least-privilege (новых прав не вводим, ADR-0022).

**Решение.** Собираем matched rules **чистым обходом CSSOM в content-скрипте**, а не через CDP.
1. **Путь (ВЫБРАН).** `document.styleSheets` → рекурсивный обход `cssRules` (включая grouping-правила `@media`/`@supports`/`@layer` с учётом применимости через `matchMedia`/`CSS.supports`) → для каждого `CSSStyleRule` матч через `el.matches(selectorText)` (**источник истины матча**) → расчёт specificity `(a,b,c)` по CSS Selectors L3 (`shared/inspection/rules/specificity.ts`, только для упорядочивания) → атрибуция победителя на каждое свойство каталога. Модуль `shared/inspection/rules/{specificity,collector,types}.ts`; снимок `MatchedRulesResult` валидируется `MatchedRulesSchema` на UI-границе.
2. **Аддитивная интеграция — без нового контракта.** Форма `data` сборщика `'probe'` расширена **аддитивным** полем `rules: MatchedRulesResult | null` (та же `inspection/collect`, тот же id `'probe'`); композиция в `collectElementProps`. **Нового RPC, id сборщика, сообщения и права — нет** (ровно как TASK-054 расширил форму `data`). Пересчёт на каждый шаг навигации/клик даёт существующий авто-`collect` хука `useInspectedNode` (TASK-052/056).
3. **Единый источник правды свойств.** Атрибуция «кто задал свойство» и объявления правил ограничены тем же `PROP_CATALOG`, что и computed-профиль (`props/catalog.ts`) — связывает значение свойства с правилом, второй список не заводим.
4. **Каскад — по правилам.** Порядок победителя: `origin` (inline vs author) → `@layer` → specificity → порядок в источнике; `!important` инвертирует (author-important бьёт inline-normal). Детерминированный порядок правил/объявлений — для стабильных снапшотов.
5. **Приватность.** Inline-`style` входит **строго** как разобранные CSS-пары из каталога, не как сырой атрибут и не `value`/текст полей (согласовано с denylist `style`/`value` в `props/catalog.ts`); в логи — ничего со страницы.

**Почему не CDP (отклонён как primary).** CDP `CSS.getMatchedStylesForNode` через `chrome.debugger` точнее (UA-стили, inherited, pseudo, cross-origin, точные диапазоны строк), но: (1) требует право `debugger` — **install-time** и с **install-warning** (ADR-0038, [PERMISSIONS.md](PERMISSIONS.md)), в отличие от host-гейтных прав слоя; (2) показывает **баннер отладки** (минус CDP, PRD §13); (3) **решающее:** `chrome.debugger.attach` **конфликтует с уже открытым DevTools** на вкладке — а QA, разбирающий каскад, почти всегда держит DevTools открытым, то есть CDP откажет ровно в основном сценарии аудитории.

**Следствия.** (+) Least-privilege: без новых прав/манифеста и баннера, работает **параллельно с открытым DevTools**. (+) Канон слоя: чистый `(el) => сериализуемые данные`, ~100% покрытие юнитами в jsdom с инъекцией источников; границы сред и «DOM не мутируется» соблюдены строго. (+) Аддитивность: контракт `inspection/collect`, host- и probe-тесты, старые снапшоты профиля без `rules` — остаются зелёными. (−) **Нет UA-стилей** (стили браузера по умолчанию недоступны в CSSOM) — помечаем как известный разрыв с DevTools. (−) **Cross-origin стайлшиты** без CORS бросают `SecurityError` на `sheet.cssRules` — ловим, считаем нечитаемые листы и показываем честную плашку «N внешних таблиц недоступны (CORS)», а не делаем вид, что правил нет. (−) **Нет точных номеров строк** в `.css` (без sourcemap/парсинга текста) — отдаём href + селектор. Все ограничения **маркируются в UI**, не замалчиваются.

**Альтернативы.** (а) **CDP `CSS.getMatchedStylesForNode`** — точнее, но право `debugger`/баннер/конфликт с DevTools (см. выше); **отклонено** как primary. При реальном спросе на UA-стили/cross-origin — отдельный **opt-in «глубокий каскад» на CDP** из бэклога (включается явным жестом, честно предупреждает про баннер/конфликт); базовый matched-rules остаётся на CSSOM. (б) **Свой матчер селекторов** вместо `el.matches` — отклонено: дублирует движок браузера и неизбежно расходится; `el.matches` — источник истины, парсер specificity нужен лишь для порядка. (в) **Дамп всех объявлений правила** (не по каталогу) — отклонено: шумно и расширяет приватную поверхность; ограничиваем каталогом (один источник правды с профилем).

## ADR-0053: Откреплённая плавающая панель — content-обёртка (closed Shadow DOM) + iframe на extension-страницу с переиспользованием `QASurface`; drag/lifecycle по `postMessage` c nonce; `web_accessible_resources` вместо новых прав — TASK-062

**Статус:** Accepted · **Дата:** 2026-10-05

**Контекст.** Основной UI жил в action popup и side panel. Popup прибит к тулбару и закрывается на `blur` (клик по странице его убивает); side panel персистентен, но докнут к краю окна. Пользователь хочет **третий способ** — перетаскиваемую поверхность поверх самой страницы, которую можно оставить открытой рядом с проверяемым элементом и двигать куда удобно. Это аддитивная, третья точка монтажа той же `QASurface` (вариант `panel`) рядом с popup/side panel; те не трогаются. Инварианты (PRD 6/9/10, TASK-013, ADR-0013/0020/0022): DOM страницы не мутируется, DOM-узлы не пересекают границу сред, сети слой не делает, least-privilege — новых permission не вводим.

**Решение.** Панель — **closed-Shadow-DOM content-обёртка** (рамка + drag-handle заголовок со свернуть/закрыть) с **cross-origin `<iframe>`** внутри на extension-страницу `src/panel/index.html#<nonce>`, рендерящую `QASurface variant="panel"`.
1. **Переиспользование UI целиком.** Весь shell/тема/`global.css`/i18n/реестр фич едут в iframe без переписывания; инвариант «не мутируем DOM/стили страницы» выполняется тривиально (iframe — другой origin). Отклонён «чистый Shadow-mount Preact» (пришлось бы переинжектить `global.css`/тему/`ToastProvider` в shadow root вручную) — держим его как явный фолбэк, если framing окажется проблемным на многих сайтах.
2. **RPC к странице не меняется.** iframe — extension-контекст, говорит с background тем же `chrome.runtime`-bus, что popup/side panel; инспектор и прочие инструменты внутри панели работают через существующий `installInspectionForwarding` → `tabs.sendMessage(tabId)` → content-хост в топ-фрейме. Новый транспорт к странице не нужен.
3. **Обёртка без runtime-роутера.** Обёртка (content-скрипт `content-panel.js`) делает только DOM/drag/persist и `postMessage`-координацию со своим iframe; она НЕ поднимает `chrome.runtime`-роутер — иначе второй роутер в том же isolated-world конфликтовал бы с инспекционным. Поэтому инъекция идемпотентна **guard-флагом** (`window.__qatb_panel__`), без ping-пробы (обобщённый `background/inject.ts` параметризован: инспекция с ping, панель без).
4. **Drag — prod-grade.** Pointer Events + `setPointerCapture`, `touch-action: none`, позиционирование `transform: translate3d`, мягкий clamp (на экране всегда весь заголовок), reclamp на `resize`; на время драга `pointer-events` iframe гасятся (иначе курсор «проваливается» в iframe). `pointercancel`/потеря capture — штатное завершение.
5. **Безопасность `postMessage`.** Каждое служебное сообщение обёртка↔iframe несёт per-mount крипто-nonce (в `#hash` URL iframe); обе стороны валидируют marker+nonce+zod-схему и игнорируют чужое — скрипт страницы видит iframe, но без nonce не закроет/не подвинет панель.
6. **`web_accessible_resources`, а не право.** Тело панели фреймится веб-страницей, поэтому `src/panel/index.html` объявлен web-accessible (`use_dynamic_url: true` — анти-фингерпринт; `matches: ['*://*/*']` — http/https, без `file://`, согласованно с ADR-0022). Это **декларация, не permission** — install-warning не поднимает; host/`scripting` уже optional из брокера, новых прав нет.
7. **Window chrome — в обёртке (осознанное уточнение задачи).** Drag-handle заголовок со свернуть/закрыть рисует обёртка (единый оконный chrome), а не iframe: контролы остаются рабочими даже при фолбэке (строгая CSP не даёт загрузить тело). `QASurface variant="panel"` поэтому лишь (а) разрешает `PANEL_ONLY`-инструменты (панель персистентна, как side panel) и (б) скрывает аффорданс «открепить»; close/collapse не дублирует. Мост iframe→обёртка (`PanelBridge`) обязателен для `ready` (иначе обёртка по дедлайну уходит в CSP-фолбэк) и поддерживает collapse/close/resize-намерения на будущее.
8. **Деградация при строгой CSP.** `frame-src`/`frame-ancestors` страницы может заблокировать фрейминг extension-страницы. Детектируем по таймауту `ready` → показываем локализованный фолбэк **внутри обёртки** (а не тост в UI: контрол закрытия остаётся под рукой), не оставляя битого iframe.

**Следствия.** (+) Полное переиспользование `QASurface` без ретрофита; «DOM не мутируется» соблюдён физически (origin iframe). (+) Least-privilege: без новых прав/манифест-варнингов; `web_accessible_resources` — только документ панели. (+) Аддитивно: popup/side panel, инспектор (одноразовый/живой) и инъекция — зелёные; `ensureContentScript` обобщён без смены поведения (inspection-тесты без правок). (+) Инспектор исключает `[data-qatb-panel]` из обхода/пикера (единый селектор в `shared/inspection/dom.ts`) — панель не «видит сама себя». (−) На страницах со строгой `frame-src`-CSP тело не грузится — честный фолбэк, задокументированное ограничение (фолбэк-путь «чистый Shadow-mount» держим в резерве). (−) closed Shadow DOM недоступен Playwright'у — drag/clamp/collapse закрыты юнитами (синтетические Pointer Events / фейковый DOM), e2e проверяет инъекцию/персист/lifecycle/DOM-неизменность/CSP.

**Альтернативы.** (а) **Чистый Shadow-mount `QASurface` в shadow root** (без iframe) — легче, но требует переинжекта `global.css`/темы/`ToastProvider` и рискует протечкой стилей страницы в сложную поверхность; **отклонено** как primary, оставлено явным фолбэком. (б) **Чистый iframe без Shadow-обёртки** — идеальная изоляция тела, но хост-`<div>` в light-DOM → CSS страницы дотянется до рамки/хэндла; **отклонено** (Shadow-обёртка дёшева). (в) **Свой транспорт обёртка→страница для RPC** — не нужен: iframe уже ходит к background обычным bus; `postMessage` оставлен строго под drag/lifecycle/size.
